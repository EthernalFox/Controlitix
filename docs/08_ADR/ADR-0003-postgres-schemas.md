# ADR-0003: Разделение PostgreSQL на схемы и разрешение кросс-схемных FK

- Статус: accepted
- Дата: 2026-04-15
- Авторы: команда Controlitix

## Контекст

В Controlitix данные логически разделены на несколько доменов: объекты и мнемосхемы, устройства, теги, история значений, тревоги, пользователи и аудит. На MVP используется одна инсталляция PostgreSQL на хост, но заказчик планирует в будущем переход в SaaS/облако, где может потребоваться изоляция групп таблиц.

Дополнительный вопрос: ранее в документации был зафиксирован запрет кросс-схемных FK. Это затрудняет поддержание ссылочной целостности между `devices.devices.object_id` и `public.objects.id`, и вступает в противоречие с реальной моделью.

## Рассмотренные варианты

### По разделению на схемы

1. **Все таблицы в `public`** — просто, но стирает доменные границы.
2. **Несколько логических схем внутри одной БД** — сохраняет доменные границы, облегчает будущую миграцию (можно выносить схемы в отдельные БД/сервисы).
3. **Несколько физических БД с одного старта** — избыточно для MVP, усложняет транзакции и backup.

### По кросс-схемным FK

1. **Запретить кросс-схемные FK** — требует писать логику целостности на уровне приложения, легко допустить орфан-записи.
2. **Разрешить кросс-схемные FK** — стандартная PostgreSQL-возможность, работает прозрачно.

## Решение

### Схемы

Разделяем PostgreSQL на следующие **схемы** внутри одной БД:

| Схема | Назначение |
|---|---|
| `public` | Объекты мониторинга, мнемосхемы, фигуры, параметры фигур |
| `devices` | Устройства, типы устройств, параметры подключения |
| `tags` | Теги, параметры тегов, справочники типов данных и единиц, масштабирование, уставки |
| `history` | Архив значений тегов, TimescaleDB hypertables, continuous aggregates |
| `alarms` | Тревоги, события тревог, квитирования |
| `auth` | Пользователи, роли, токены, telegram_chats, audit_log |

Разделение сознательное — оно упрощает будущий переход к SaaS-модели: при необходимости отдельные схемы можно вынести в независимые БД или даже в отдельные сервисы без массовой переработки.

### Кросс-схемные FK

**Разрешаем** кросс-схемные FK в MVP. PostgreSQL поддерживает их штатно, дополнительной сложности нет. Для будущего разделения по независимым БД такие FK станут ограничением — тогда мы их заменим на приложенческие проверки, но делать это сейчас преждевременно.

Конкретные кросс-схемные связи, которые будут существовать:

- `devices.devices.object_id → public.objects.id`
- `tags.tags.device_id → devices.devices.id`
- `history.*` — **без FK** на `tags.tags` (высокая нагрузка, hypertable).
- `alarms.*.tag_id` — **без FK** на `tags.tags` (логическая связь, ссылочная целостность поддерживается приложением).
- `public.figures.tag_id` — **без FK** (как сейчас, логическая связь).

## Последствия

**Позитивно:**

- Чёткие доменные границы на уровне БД.
- Заготовка под SaaS: схемы легко отделить.
- FK обеспечивают базовую целостность конфигурации без приложенческой логики.
- Противоречие в документации устранено.

**Негативно:**

- Миграции становятся чуть сложнее: нужно создавать схемы перед таблицами.
- При будущем переезде отдельных схем в независимые БД придётся вручную убирать кросс-схемные FK и заменять на приложенческие проверки.
- Разработчикам нужно держать в голове, какая таблица в какой схеме.
