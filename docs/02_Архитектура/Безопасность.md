# 2.6 Безопасность

Документ описывает модель угроз, контроли и границы безопасности Controlitix MVP. Детали аутентификации — в [`Микросервисы/ms-auth.md`](Микросервисы/ms-auth.md) и [ADR-0012](../08_ADR/ADR-0012-ms-auth-pluggable-identity.md).

## Контур

- **Self-hosted, внутренняя сеть заказчика.** Платформа не выходит во внешний интернет, за исключением исходящих вызовов Telegram Bot API.
- **Один физический хост на объект**, Docker Compose ([ADR-0005](../08_ADR/ADR-0005-docker-compose-mvp.md)).
- **Единая точка входа** — Nginx ([ADR-0006](../08_ADR/ADR-0006-nginx-gateway.md)), TLS-термирование.
- **Personal data:** не обрабатывается (см. НФТ).
- **Шифрование at rest:** не требуется (решение заказчика, НФТ).

## Доверительные зоны

```
┌──────────────────────────────────────────────────────────────────┐
│ LAN предприятия                                                 │
│  ┌─────────────┐        ┌────────────────────────────────────┐  │
│  │ Пользователь│ HTTPS  │ Хост Controlitix                   │  │
│  │ (браузер)   ├────────▶ ┌───────┐                          │  │
│  └─────────────┘        │ │ nginx │  TLS, routing, статика   │  │
│                         │ └───┬───┘                          │  │
│                         │     │ HTTP внутри Docker network  │  │
│                         │ ┌───▼────────────────────────────┐ │  │
│                         │ │ ms-auth, ms-editor, ms-poll,   │ │  │
│                         │ │ ms-viewer  +  PG / Redis / KFK │ │  │
│                         │ └────────────────────────────────┘ │  │
│                         └────────────────────────────────────┘  │
└──────────────────────────────────────────────────────────────────┘
                                           │
                                           ▼ HTTPS (исходящий)
                                     Telegram Bot API
```

Внутри Docker network нет mTLS — доверенная зона за Nginx ([ADR-0007](../08_ADR/ADR-0007-service-accounts-env-secrets.md)). Аутентификация сервисов друг перед другом — через ТУЗ + JWT.

## Идентичность и аутентификация

### Пользователи

- Единый провайдер — `ms-auth`. Три роли: `admin`, `engineer`, `operator`.
- Пароли — Argon2id + pepper из env.
- Сессия клиента — access-JWT (15 мин) + opaque refresh-token (14 дней) с ротацией.
- Источник идентичности — pluggable. В MVP — `local`. Архитектурно поддерживаются (реализации появятся после MVP):
  - **LDAP** — простой корпоративный каталог.
  - **Active Directory** — LDAP-совместимый + `objectGUID` как стабильный `subject` + nested groups.
  - **Kerberos / SPNEGO** — Windows-домен, прозрачный логин без ввода пароля.
  - **OIDC federation** — Keycloak / ADFS / AzureAD через `authorization_code + PKCE`.

Подробнее о миграционном пути — в [ADR-0012](../08_ADR/ADR-0012-ms-auth-pluggable-identity.md).

### Сервисы (ТУЗ)

- Каждый сервис имеет свой `client_id` и `client_secret` в `auth.service_accounts`.
- Получает service-JWT через `client_credentials`, TTL 15 мин, без refresh.
- Валидирует входящие JWT локально через JWKS ms-auth ([ADR-0006](../08_ADR/ADR-0006-nginx-gateway.md)).

### JWT

- RS256, kid-ротация (ручная в MVP).
- `aud=controlitix-api` для пользователей, `aud=controlitix-internal` для сервисов.
- `sub` стабильный и независимый от источника (`local:<uuid>` / `ad:<guid>` / `svc:<name>` / ...).
- Клеймы `roles`, `scope` используются приёмниками для RBAC.

## Авторизация

### MVP

- **Глобальные роли** — `admin` / `engineer` / `operator`.
- Проверка на уровне middleware каждого сервиса (`shared/authctx`).
- Admin-эндпоинты `ms-auth` доступны только `admin`.
- `engineer` имеет CRUD-доступ к `ms-editor`.
- `operator` — только чтение в `ms-viewer`, квитирование тревог.
- `svc:*` — scope-ориентированный доступ (например, `ms-poll` имеет `tags.values.write` и `config.read`, но не может вызвать admin endpoints).

### За пределами MVP

- Per-object RBAC (ограничение по `monitoring_object_id` / мнемосхеме).
- Policy engine (OPA / Cedar) — если сложность RBAC вырастет.
- ABAC-атрибуты (время суток, IP, контекст).

## Секреты

См. [ADR-0007](../08_ADR/ADR-0007-service-accounts-env-secrets.md).

| Секрет | Где хранится | Кто читает |
|---|---|---|
| `POSTGRES_PASSWORD` | `.env` хоста | все сервисы |
| `MS_*_CLIENT_SECRET` (ТУЗ) | `.env` хоста | свой сервис + ms-auth (хэш) |
| `MS_AUTH_JWT_PRIVATE_KEY` | `.env` хоста | только ms-auth |
| `MS_AUTH_PASSWORD_PEPPER` | `.env` хоста | только ms-auth |
| `TELEGRAM_BOT_TOKEN` | `.env` хоста | ms-viewer |
| TLS-сертификат | файловая система, `.env` — путь | nginx |

Ротация — ручная с перезапуском. Vault / KMS — вне MVP; целевое состояние — приватный ключ JWT и pepper переедут в Vault первыми при его внедрении.

## Хэширование и криптография

| Где | Алгоритм | Параметры |
|---|---|---|
| Пароль пользователя | Argon2id + pepper | m=64 MiB, t=3, p=2 |
| Хэш client_secret ТУЗ | Argon2id + pepper | те же |
| Хэш refresh-токена в БД | SHA-256 | opaque-токен, HMAC не требуется |
| Подпись JWT | RS256 | 2048-bit ключ |
| TLS | TLS 1.2+ | сертификат самоподписанный или корпоративный |

## Сетевая модель

- Nginx — единственный открытый порт наружу (443).
- Telegram — исходящий 443 к `api.telegram.org`.
- Внутри Compose network — никаких публичных портов сервисов.
- Межсервисный трафик — HTTP (plaintext) внутри Docker bridge; защита — изоляция сети и ТУЗ-JWT.

## Аудит

- События безопасности пишутся в `auth.audit_log` и публикуются в Kafka `audit.logs` ([ADR-0010](../08_ADR/ADR-0010-kafka-event-bus.md)).
- Минимальный набор событий:
  - `login.success` / `login.failure` (с reason).
  - `token.refresh`, `token.revoke`, `token.reuse_detected`.
  - `service_token.issue` / `service_token.failure`.
  - `admin.user.*`, `admin.role_assignment.*`, `admin.service_account.*`.
- Retention Kafka `audit.logs` — 90 дней (по ADR-0010). Sink в отдельное хранилище — вне MVP.

## Rate limiting

- `/api/auth/login` — N неудач за M минут → 429. Ключ: `ip + username`.
- `/api/auth/refresh`, `/api/auth/service-token` — защита от массового перебора refresh.
- Реализация — Redis-счётчики; допустимо in-memory при отсутствии Redis (single-instance режим).
- Нет account lockout — только rate limit.

## Модель угроз (кратко)

| Угроза | Митигация |
|---|---|
| Кража access-токена | Короткий TTL (15 мин), HTTPS, SameSite cookie |
| Кража refresh-токена | Rotation + reuse detection → инвалидация семьи |
| Компрометация БД | Pepper отдельно от БД, Argon2id → offline brute-force нерентабелен |
| Компрометация `.env` файла | Права `0600`, физическая безопасность хоста, monitoring |
| Подделка JWT | RS256, приватный ключ только у ms-auth |
| Повторные попытки логина | Rate limit на `/login` |
| SQL injection | Параметризованные запросы, pgx |
| XSS в editor-ui/viewer-ui | Строгий CSP в nginx, React-экранирование |
| CSRF | Refresh в httpOnly+SameSite cookie, access — в Authorization header |
| Перехват трафика в LAN | TLS на Nginx; внутри Compose — доверенная зона |
| Эскалация прав | Audit log, ревью admin-действий |
| Отказ в обслуживании | Rate limit, health-пробы, graceful degradation; защита DDoS — вне MVP |
| Компрометация одного сервиса | Scoped-токены ТУЗ: `ms-poll` не может трогать admin endpoints |
| Инсайдер с доступом к хосту | Outside MVP — системные средства (SELinux, аудит ОС) |

## Чего в MVP нет (осознанно)

- Шифрование at rest для БД и Kafka.
- mTLS между сервисами.
- Secrets management (Vault).
- Автоматическая ротация ключей.
- MFA для пользователей.
- Attestation устройств.
- Network segmentation внутри Compose.
- WAF перед Nginx.
- DDoS-защита.
- Формальный pentest и threat model.

Планируемое расширение — после пилота, по запросу заказчика, через отдельные ADR.

## ms-viewer RBAC (spec 0036)

Endpoint to role mapping:
- `GET /api/trends*`, `GET /api/tags`, `GET /api/objects*`, `GET /api/diagrams*`, `GET /api/alarms*` => `operator|engineer|admin`
- `POST /api/alarms/{tagId}/acknowledge` => `operator|admin`
- `GET /api/notifier/chats` => `engineer|admin`
- `GET /api/ws` (upgrade) => `operator|engineer|admin`

Forbidden access is returned as `403 /errors/auth/forbidden` and is written to `audit.logs` as `auth.forbidden`.
