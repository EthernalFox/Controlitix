# 0045: editor-ui — LoginPage + auth-store + интеграция с ms-auth

## Scope

`editor-ui/src/`:
- `pages/LoginPage/`
- `app/providers/AuthProvider/`
- `features/auth/`
- `shared/api/` — токен-инжекция и refresh-loop
- `shared/libs/router/` — `ProtectedRoute`

Бэкенд не трогаем. Используем готовые эндпоинты `ms-auth` (`POST /api/auth/login`, `POST /api/auth/refresh`, `POST /api/auth/logout`, `GET /api/auth/userinfo`) — контракт зафиксирован в спеке 0022.

Эта спека — **порт 0027 (viewer-ui-login) на editor-ui** с учётом отличий: editor-ui — инженерная UI, дефолтная тема — светлая (см. Design-System.md), точка входа после логина — `/objects` (не `/`).

## Context

`editor-ui` сейчас не имеет логина: все экраны открыты любому, кто открыл URL. После Phase 1 (ms-auth) и спеки 0024 (`shared/authctx` middleware на стороне `ms-editor`) backend начинает требовать JWT — без логина инженерная UI перестанет работать.

Ссылочная реализация — `viewer-ui/src/{pages/LoginPage,app/providers/AuthProvider,features/auth,shared/api/auth-token.ts,shared/libs/router/ProtectedRoute.tsx}` (спека 0027). При расхождениях между этой спекой и кодом 0027 — побеждает 0027 (он `done`).

Контракт ms-auth — [specs/0022.done.ms-auth-http-auth.md](0022.done.ms-auth-http-auth.md):

- `POST /api/auth/login` — body `{ "username", "password" }` → 200 `{ access_token, token_type:"Bearer", expires_in, refresh_token, user{...} }` + `Set-Cookie: refresh_token=...; HttpOnly; Secure; SameSite=Strict; Path=/api/auth`.
- `POST /api/auth/refresh` — без тела (refresh-cookie сам летит) → 200 `{ access_token, token_type, expires_in, refresh_token }`.
- `POST /api/auth/logout` → 204.
- `GET /api/auth/userinfo` — `Authorization: Bearer` → 200 `{ subject, username, email, roles[], ... }`.

Коды ошибок (RFC 7807):
- `401 /errors/auth/invalid-credentials`, `/errors/auth/invalid-refresh`, `/errors/auth/invalid-token`, `/errors/auth/token-expired`.
- `403 /errors/auth/user-disabled`.
- `429 /errors/auth/rate-limited` + `Retry-After`.
- `503 /errors/auth/source-disabled`.

Роли: `admin`, `engineer`, `operator`. **editor-ui требует `engineer` или `admin`**; пользователь с ролью только `operator` после логина должен получить страницу `/access-denied` со ссылкой на `viewer-ui`.

## Interface

### `authStore` (Zustand)

```ts
type AuthUser = {
  subject: string;
  username: string;
  email: string | null;
  roles: string[];
};

type AuthStatus =
  | "idle"            // первичное состояние до bootstrap
  | "authenticating"  // /login или /refresh в процессе
  | "authenticated"
  | "unauthenticated";

interface AuthState {
  status: AuthStatus;
  accessToken: string | null;
  expiresAt: number | null;     // unix ms
  user: AuthUser | null;
  lastError: string | null;     // RFC 7807 type, например "/errors/auth/invalid-credentials"

  login(username: string, password: string): Promise<void>;
  refresh(): Promise<void>;
  logout(): Promise<void>;
  bootstrap(): Promise<void>;
}
```

`accessToken` хранится **только в памяти**.

### `LoginForm`

Поля: `username` (autofocus, required), `password` (required), кнопка «Войти».

Сообщения по `lastError`:
- `/errors/auth/invalid-credentials` → «Неверный логин или пароль».
- `/errors/auth/user-disabled` → «Учётная запись отключена. Обратитесь к администратору».
- `/errors/auth/rate-limited` → «Слишком много попыток. Повторите через N секунд» (показать Retry-After, блокировать форму на N секунд).
- `/errors/auth/source-disabled` → «Сервис аутентификации недоступен. Попробуйте позже».
- сетевая ошибка → «Не удалось связаться с сервером».
- прочее → «Не удалось выполнить вход».

После успешного `login()` — проверка роли:
- Если `hasEditorRole(user)` → `navigate(state.from ?? "/objects")` с `replace: true`.
- Иначе → `navigate("/access-denied", { replace: true })`. Сессия остаётся валидной (чтобы AccessDeniedPage могла вызвать `logout`).

### Bootstrap flow (на mount AuthProvider)

```
1. status = "authenticating"
2. userinfo() (accessToken null после холодной загрузки → 401).
   - 200 → user, status = "authenticated".
   - 401 → перейти к refresh.
3. refresh() — без явного refresh_token, cookie летит сама.
   - 200 → setAccessToken, expiresAt; затем userinfo() снова.
   - 401/403 → status = "unauthenticated".
   - сеть упала → status = "unauthenticated", lastError = network.
4. После status = authenticated:
   - Если !hasEditorRole(user) → router.navigate("/access-denied", { replace: true }).
```

`ProtectedRoute` ждёт перехода `idle/authenticating` → терминальное состояние. До этого — `<Loader />` на весь экран. Никаких мерцаний контента.

`ProtectedRoute` дополнительно: если `authenticated` но `!hasEditorRole(user)` → редирект `/access-denied`. Это страховка на случай прямого захода по защищённому URL.

### Refresh-loop

- **Реактивный**: при 401 — один параллельный `refresh()`, все одновременные запросы ждут одного in-flight promise (мьютекс в `tokenScheduler`).
- **Проактивный**: после `setAccessToken` — `setTimeout` на `expiresAt - now - 60_000`. По истечении — `refresh()`. Сбрасывается на новый `setAccessToken` или `logout`.

Если `refresh()` упал (401/403) — локальный `clearAccessToken()` + reset store, редирект `/session-expired`.

### Logout

`logout()`:
1. `POST /api/auth/logout` — игнорировать ошибки (всегда 204 ожидаем).
2. `clearAccessToken()`, обнулить store.
3. `navigate("/login", { replace: true })`.

### TypeScript-контракты DTO

```ts
// shared/modules/auth/types.ts
export interface LoginRequest { username: string; password: string; }

export interface LoginResponse {
  accessToken: string;
  tokenType: "Bearer";
  expiresIn: number;
  refreshToken?: string;

  accessToken: string;

```

Имена в TS — camelCase; клиент `shared/api/client.ts` уже делает snake→camel (см. существующую реализацию editor-ui).

## Constraints

- Access-токен **только в памяти**. Не в localStorage/sessionStorage/IndexedDB. Та же политика, что в 0027.
- Refresh-токен **никогда** не доступен JS. Только HttpOnly cookie. Если ms-auth прислал `refreshToken` в теле — игнорировать.
- При 401 — **один** retry с refresh. Цикл `401→refresh→401` запрещён.
- В `LoginForm` пароль только в локальном `useState`, очищать после submit, не класть в Zustand.
- Не использовать `axios` или иные HTTP-обёртки. Только `fetch` через `shared/api/client.ts`.
- `ProtectedRoute` **не мигает** контентом — Loader → редирект или контент.
- `redirect after login` — на `state.from` или `/objects`. Не редиректить на `/login`/`/access-denied`/внешние URL (open-redirect).
- В UI не показывать `lastError` со значениями типа `/errors/auth/...` — только локализованные тексты.
- Тексты — русский.
- `/api/auth/*` — через `shared/api/client.ts`, но `/login` и `/refresh` НЕ должны триггерить refresh-loop при 401 (это валидный отказ).
- AccessDeniedPage **сохраняет** валидную сессию (не вызывает logout автоматически). У пользователя должен быть выбор: уйти в viewer-ui или явно выйти.
- Проверка ролей `hasEditorRole` — централизованная функция, не разбросана по компонентам. На добавление новой роли (будущее) — менять одно место.
- Стили: editor-ui по умолчанию светлая тема (Design-System.md). LoginPage — без AppShell (Header/Sidebar спрятаны до логина).
- Нет импортов `@mantine/core` напрямую из `pages/LoginPage`, `pages/AccessDeniedPage`, `pages/SessionExpiredPage`, `widgets/UserMenu` — только через `shared/ui/components` (правило проекта).
- НЕ добавлять отдельный пакет `shared/auth-spa` для унификации с viewer-ui в этой спеке. Это рефакторинг, обсуждается отдельно. Сейчас — копия с adjustments под editor-ui (DRY < проектные сроки).

## Review notes

### 1. Отсутствует файл `app/providers/AuthProvider/AuthProvider.tsx`

Спека явно требует этот файл как точку bootstrap-а (вызов `authStore.bootstrap()` на mount + Loader до завершения инициализации). Файл не создан.

**Исправление:** создать `editor-ui/src/app/providers/AuthProvider/AuthProvider.tsx`:

```tsx
import { useEffect } from "react";
import { useAuthStore } from "@features/auth";
import { Loader } from "@shared/ui/components";

interface AuthProviderProps {
  children: React.ReactNode;
}

export function AuthProvider({ children }: AuthProviderProps) {
  const { status, bootstrap } = useAuthStore();

  useEffect(() => {
    bootstrap();
  }, []);

  if (status === "idle" || status === "authenticating") {
    return <Loader size="xl" style={{ display: "flex", alignItems: "center", justifyContent: "center", height: "100vh" }} />;
  }

  return <>{children}</>;
}
```

Затем обернуть в `app/App.tsx`:
```tsx
// Порядок: AuthProvider поверх RouterProvider (или внутри, если используется imperative navigate)
<AuthProvider>
  <RouterProvider />
</AuthProvider>
```

### 2. Bootstrap: неявная проверка 401 перед refresh

В `authStore.ts` bootstrap вызывает `userinfo()`, и при любой ошибке (не только 401) переходит к `refresh()`. Если `ms-auth` недоступен (503), bootstrap делает лишний `refresh`-запрос.

**Исправление:** явно проверить статус ошибки перед вызовом refresh:

```ts
try {
  const user = await userinfo();
  // ... authenticated
} catch (err) {
  const is401 = err instanceof ApiError && (err.status === 401 || err.payload?.type?.includes("token-expired") || err.payload?.type?.includes("invalid-token"));
  if (!is401) {
    // Сетевая или серверная ошибка — не пытаться refresh
    set({ status: "unauthenticated", lastError: "network" });
    return;
  }
  // 401 → попробовать refresh
  try {
    await refresh();
    const user = await userinfo();
    // ... authenticated
  } catch {
    set({ status: "unauthenticated" });
  }
}
```

Это предотвращает бесполезный `POST /api/auth/refresh` при недоступности сервиса и делает поведение предсказуемым.
