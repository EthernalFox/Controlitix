# 0029: ms-viewer — Skeleton + history-ingest + REST trends

## Scope

Каталог `ms-viewer/` (сейчас содержит только `README.md`). Спека закрывает:

1. Скелет Go-сервиса (config, slog, chi, healthz/readyz, graceful shutdown, миграции через Goose).
2. Схему `history` в PostgreSQL c TimescaleDB (hypertable + continuous aggregate + retention/compression).
3. Kafka-консьюмер `tags.values` → запись raw-значений в `history.tag_values_raw` + обновление кэша последних значений в Redis.
4. REST-эндпоинты трендов из контракта спеки 0028: `GET /api/trends/{tagId}`, `GET /api/trends`.
5. Проксирование `GET /api/tags?search=...` (для `TrendTagPicker` из 0028) — read-only, к таблице `tags.tags` той же БД.
6. JWT-валидация через shared/authctx (спека 0024) — все `/api/*` эндпоинты под auth.

Out of scope этой спеки: realtime/WS (0030), alarms-engine, notifier (Telegram), `config.changed`-консьюмер.

### Migrations (`ms-viewer/migrations/`)

`000001_init_history.sql`:

```sql
-- +goose Up
CREATE SCHEMA IF NOT EXISTS history;

CREATE EXTENSION IF NOT EXISTS timescaledb;

CREATE TABLE history.tag_values_raw (
    tag_id   uuid        NOT NULL,
    ts       timestamptz NOT NULL,
    v        double precision NULL,
    q        smallint    NOT NULL,        -- enum-int (см. domain.QualityCode)
    PRIMARY KEY (tag_id, ts)
);

SELECT create_hypertable('history.tag_values_raw', 'ts', chunk_time_interval => INTERVAL '1 day');

CREATE INDEX tag_values_raw_tag_ts_idx
    ON history.tag_values_raw (tag_id, ts DESC);

ALTER TABLE history.tag_values_raw SET (
    timescaledb.compress,
    timescaledb.compress_segmentby = 'tag_id',
    timescaledb.compress_orderby   = 'ts DESC'
);

SELECT add_compression_policy('history.tag_values_raw', INTERVAL '7 days');
SELECT add_retention_policy  ('history.tag_values_raw', INTERVAL '30 days');

CREATE MATERIALIZED VIEW history.tag_values_1m
WITH (timescaledb.continuous) AS
SELECT
    tag_id,
    time_bucket(INTERVAL '1 minute', ts) AS bucket,
    avg(v)            AS avg,
    min(v)            AS min,
    max(v)            AS max,
    count(v)          AS count,
    last(v, ts)       AS last,
    last(q, ts)       AS q
FROM history.tag_values_raw
GROUP BY tag_id, bucket
WITH NO DATA;

SELECT add_continuous_aggregate_policy('history.tag_values_1m',
    start_offset      => INTERVAL '7 days',
    end_offset        => INTERVAL '1 minute',
    schedule_interval => INTERVAL '1 minute');

SELECT add_retention_policy('history.tag_values_1m', INTERVAL '365 days');

-- +goose Down
SELECT remove_retention_policy('history.tag_values_1m', if_exists => true);
SELECT remove_continuous_aggregate_policy('history.tag_values_1m', if_exists => true);
DROP MATERIALIZED VIEW IF EXISTS history.tag_values_1m;
SELECT remove_retention_policy('history.tag_values_raw', if_exists => true);
SELECT remove_compression_policy('history.tag_values_raw', if_exists => true);
DROP TABLE IF EXISTS history.tag_values_raw;
DROP SCHEMA IF EXISTS history;
```

`tags.tags` и `public.objects` — не создаём, читаем как есть из общей БД (владельцы — `ms-editor` и `ms-auth`). DB-роль `ms_viewer` должна иметь `SELECT` на эти таблицы и `INSERT/SELECT` на `history.*`.

### REST endpoints

#### `GET /api/trends/{tagId}`

Query: `from`, `to` (RFC3339, обязательны); `step` (`5s|1m|...`), `agg` (`last|avg|min|max`, default `avg`), `limit` (default 1000, max `TrendsMaxLimit`).

Логика usecase:
1. Валидация `from < to`, `to - from ≤ TrendsMaxRangeDays`, `limit ≤ TrendsMaxLimit`.
2. Загрузить метаинфо тега (`tag_id`, `tag_name`, `device_*`, `unit`, `data_type`) из `tags.tags`/`devices.devices`/`tags.units`/`tags.data_types`. Не нашли → 404 `/errors/trends/tag-not-found`.
3. Решить источник:
   - `to - from ≤ 24h` → `history.tag_values_raw`, источник `"raw"`.
   - `> 24h` → `history.tag_values_1m`, источник `"agg_1m"`.
4. SQL:
   - raw: `SELECT ts, v, q FROM history.tag_values_raw WHERE tag_id=$1 AND ts >= $2 AND ts < $3 ORDER BY ts ASC`. Если результат `> limit` — серверный downsampling через `time_bucket`+`agg`.
   - agg_1m: `SELECT bucket AS ts, <agg> AS v, q FROM history.tag_values_1m WHERE tag_id=$1 AND bucket >= $2 AND bucket < $3 ORDER BY bucket ASC`.
5. `step` — вычислить эффективный шаг как `MAX(requested_step, (to-from)/limit)`.
6. Сериализовать ответ (см. контракт в 0028).

Ответ — точно по контракту 0028 (поля `tag_id`, `tag_name`, `device_id`, `device_name`, `unit{}`, `data_type{}`, `from`, `to`, `step`, `agg`, `source`, `points[]`).

#### `GET /api/trends`

Параметр `tag_ids` — comma-separated UUID, `len ≤ 10`. Остальные — те же. Возвращает `{ "series": [...] }`. Внутри — параллельная (через `errgroup` с лимитом конкурентности 4) загрузка отдельных тегов; ошибка одного тега → исключить из результата и записать `errors[]: [{tag_id, problem}]` в ответ (поле `errors` — расширение контракта; добавить в [docs/04_API/ms-viewer.md](../docs/04_API/ms-viewer.md)).

#### `GET /api/tags?search=...&limit=20`

Read-only поиск по `tags.tags` (`name ILIKE '%' || $1 || '%' AND deleted_at IS NULL`), join `devices.devices` для `device_name`. Лимит 20, сортировка по `name ASC`. Ответ:

```json
{ "items": [ {"id":"...","name":"...","device_id":"...","device_name":"...","unit_symbol":"°C"} ], "total": N }
```

#### `GET /healthz` / `GET /readyz`

`healthz` — всегда 200. `readyz` — 200 если PG-ping и Redis-ping OK; 503 иначе.

### Auth middleware

Все `/api/*` под `RequireAuth(jwks, audience)` из shared/authctx (0024). Ошибки — 401 `/errors/auth/invalid-token` или `/errors/auth/token-expired` (унифицировано через тот же RFC 7807-формат).

### Errors (RFC 7807, относительные URI)

| Type | Status | Когда |
|---|---|---|
| `/errors/trends/invalid-range` | 400 | `from >= to`, `to - from > 90d`, `limit > max` |
| `/errors/trends/tag-not-found` | 404 | тег отсутствует / soft-deleted |
| `/errors/trends/forbidden` | 403 | (placeholder для RBAC, в этой спеке не используется) |
| `/errors/auth/invalid-token` / `/errors/auth/token-expired` | 401 | mw `RequireAuth` |
| `/problems/internal-error` | 500 | паника / необработанные |

`Content-Type: application/problem+json`.

### Kafka consumer (`infrastructure/kafka/`)

Топик `tags.values` (формат — JSON, см. ms-poll выходной контракт):

```json
{
  "tag_id": "uuid",
  "ts": "2026-04-25T10:00:00Z",
  "v": 75.2,
  "q": "ok"
}
```

`tag_value_handler`:
1. Парсит запись; невалидный JSON → лог `error` + `commit` (не блокировать поток).
2. Передаёт в `IngestUseCase.IngestTagValue(record)`:
   - буферизация в slice; flush по `IngestBatchSize` или `IngestFlushMs`.
   - flush делает `INSERT INTO history.tag_values_raw (tag_id, ts, v, q) VALUES ... ON CONFLICT (tag_id, ts) DO UPDATE SET v=EXCLUDED.v, q=EXCLUDED.q` (идемпотентность).
   - параллельно SET в Redis: `ms-viewer:last:<tag_id>` = `{ts, v, q}` JSON, TTL `LastValueCacheTTLSec`.
3. Kafka offset коммитится **после** успешного flush. На ошибке БД — backoff + retry; падение redis → лог + продолжить (cache best-effort).

Consumer-group: `ms-viewer-tags-values` (один сервис может держать несколько партиций; масштабирование через увеличение реплик).

## Constraints

- Clean Architecture: `domain` без зависимостей; `usecase` зависит только от `domain`; `infrastructure` реализует репозитории; HTTP-handlers — тонкие.
- Не нарушать «cross-schema FK constraints are forbidden» — `history.*` не имеет FK на `tags.tags`/`public.objects`. Только логические связи.
- Миграции — Goose, по образцу `ms-editor/migrations/`. Никаких `ALTER` существующих таблиц других сервисов.
- DB-роль для рантайм-сервиса — `ms_viewer` с минимально необходимыми правами:
  - `INSERT, SELECT, UPDATE, DELETE` на `history.*`.
  - `SELECT` на `tags.*`, `devices.*`, `public.objects` (для метаданных тегов).
  - Никаких прав на `auth.*`.
- Версии: `pgx/v5`, `segmentio/kafka-go` (как в ms-poll), `go-chi/chi/v5`, `redis/go-redis/v9`, `pressly/goose/v3`.
- TimescaleDB: `image: timescale/timescaledb:2.16-pg16` в docker-compose; в production — отдельная установка (см. ADR-0004). В миграции `CREATE EXTENSION IF NOT EXISTS timescaledb` — обязательно идемпотентно.
- Идемпотентность ingest: `INSERT ... ON CONFLICT DO UPDATE` гарантирует, что переподача того же offset’а из Kafka не дублирует строки.
- Единицы quality: в БД хранится `smallint`-код, в API — строка. Никогда не отдаём числовой код на frontend.
- Не реализовывать в этой спеке: WS, alarms, Telegram, `config.changed`-консьюмер, RBAC.
- Не использовать сторонние ORM (gorm/sqlc) — голый pgx для консистентности с другими сервисами.
- Логи — `slog` JSON-handler в production; text-handler — только dev. Структурированные ключи: `request_id`, `tag_id`, `error`, `latency_ms`.
- Все TTL и таймауты — из config, никаких magic-numbers в коде.
- Тексты ошибок RFC 7807 (`title`, `detail`) — на английском (это серверный API, frontend локализует сам).

- `GET /api/trends/<id>?from=2026-04-01T00:00:00Z&to=2026-04-25T00:00:00Z` → 200, `source: "agg_1m"`.
- `GET /api/trends/<id>?from=...&to=...` без auth → 401.
- `GET /api/trends/<id>?from=...&to=<5y_ahead>` → 400 `/errors/trends/invalid-range`.
- `GET /api/trends/<unknown-uuid>?from=...&to=...` → 404 `/errors/trends/tag-not-found`.

- Ребут сервиса во время flush → при следующем старте дубликаты обработаются `ON CONFLICT` (значения в БД корректны).
