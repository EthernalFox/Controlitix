# ADR-0010: Kafka как шина событий

- Статус: accepted
- Дата: 2026-04-15
- Авторы: команда Controlitix

## Контекст

Сервисы Controlitix асинхронно обмениваются данными: `ms-poll` публикует значения тегов, `ms-viewer` потребляет поток и раздаёт его клиентам, пишет историю, вычисляет тревоги; `ms-editor` уведомляет об изменениях конфигурации. Нужна шина, которая:

- выдерживает ~2 000–2 500 событий/с на инсталляцию;
- обеспечивает буферизацию при кратковременных сбоях потребителей;
- позволяет нескольким потребителям читать одни и те же события независимо;
- имеет понятные retention / partitioning / offsets.

## Рассмотренные варианты

1. **Kafka** — зрелая шина, стандарт де-факто для event streaming, готовые клиенты для Go, durable storage, consumer groups.
2. **Redis Streams / pub-sub** — проще, но слабее по надёжности и retention; pub/sub не гарантирует доставку, Streams хуже по масштабируемости.
3. **NATS JetStream** — легче Kafka по ресурсам, но команда менее знакома; экосистема готовых инструментов меньше.
4. **RabbitMQ** — старый и надёжный, но ориентирован на очереди (work distribution), не на streaming.
5. **Прямое gRPC/HTTP между сервисами без шины** — тесное связывание, нет буферизации, нет multi-consumer.

## Решение

Используем **Kafka** как основную шину событий.

**Топики MVP:**

| Топик | Producer | Consumers | Partition key | Retention |
|---|---|---|---|---|
| `tags.values` | ms-poll | ms-viewer | `tag_id` | 7 дней |
| `alarms.events` | ms-viewer | ms-viewer (аудит), notifier | `alarm_id` | 30 дней |
| `config.changed` | ms-editor | ms-poll, ms-viewer | `entity_id` | 7 дней |
| `audit.logs` | все | (TBD: отдельный sink) | `user_id`/`svc_id` | 90 дней |

**Принципы:**

- Схемы сообщений фиксируются в [`04_API/Kafka-схемы.md`](../04_API/Kafka-схемы.md) (TBD) как JSON Schema. Avro/Protobuf и Schema Registry — **вне MVP**.
- Идемпотентные потребители (по `(tag_id, ts)` для values, по `alarm_id` для тревог).
- DLQ-топик `*.dlq` для каждой основной темы, с ручным разбором.
- Kafka разворачивается в Docker Compose в **KRaft-режиме** (без Zookeeper).

## Последствия

**Позитивно:**

- Durable буфер: `ms-viewer` может отстать и догнать без потерь.
- Мульти-консьюмер: история, тревоги, notifier могут читать один поток независимо.
- Стандартные инструменты (kcat, kafka-ui) для диагностики.

**Негативно:**

- Kafka — «тяжёлый» процесс (JVM-контейнер), +1–2 ГБ RAM на инсталляцию. Для MVP приемлемо, но надо учесть в sizing.
- Сложнее в эксплуатации, чем Redis: нужны мониторинг consumer lag, балансировка партиций, следить за диском.
- Schema evolution без Schema Registry — дисциплинарная ответственность команды.
