# ADR-0008: Отсутствие версионирования HTTP API в MVP

- Статус: accepted
- Дата: 2026-04-15
- Авторы: команда Controlitix

## Контекст

Backend-сервисы предоставляют HTTP API для внутренних фронтендов (`editor-ui`, `viewer-ui`). В отрасли распространён подход явного версионирования через префикс `/v1/` в URL. Встаёт вопрос — нужно ли вводить его в MVP.

Важно: API Controlitix в MVP **не публичен** и не предоставляется третьим сторонам. Клиенты — фронтенды, которые разрабатываются и релизятся вместе с backend в одном монорепозитории.

## Рассмотренные варианты

1. **Версионировать с первого дня (`/v1/`)** — устоявшаяся практика, заложить задел на будущее.
2. **Не версионировать в MVP** — короче URL, меньше шума, контракты совместимы по определению (фронт + backend релизятся вместе).
3. **Header-based versioning** — совсем редкий в ops-практике вариант, неочевидный для разработчиков.

## Решение

В MVP **не версионируем** HTTP API:

- URL выглядят как `/api/editor/objects`, `/api/viewer/trends`, `/api/auth/login` — без префикса `/v1/`.
- Фронтенды и backend релизятся синхронно, разрыва версий нет.
- Ломающие изменения допускаются между релизами и оформляются в changelog.

Когда потребуется версионирование (публичный API, внешние интеграции, независимые релизы фронта и бэка) — добавим `/v1/` и оформим отдельным ADR. Введение префикса будет простой операцией: добавить alias в Nginx, обновить клиентов.

## Последствия

**Позитивно:**

- Короче URL, меньше шума.
- Отсутствие «мёртвого» версионного уровня, который никогда не менялся.
- Меньше кода маршрутизации в Go и в nginx.

**Негативно:**

- При первом же внешнем потребителе API придётся вводить версионирование. До того момента нужно быть внимательнее с ломающими изменениями, если появятся подрядчики или внешние интеграции.
- Публичная документация OpenAPI должна явно сообщать «API нестабилен, совместимость не гарантируется между релизами».
