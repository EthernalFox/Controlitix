# 0036: ms-viewer — RBAC + audit log

## Scope

`ms-viewer/internal/`:

1. RBAC: проверка ролей пользователя на каждом эндпоинте (REST + WS).
2. Audit log: запись действий пользователя в Kafka-топик `audit.logs` (общий формат с ms-auth и ms-editor).
3. Фиксация ролевой модели в [docs/02_Архитектура/Безопасность.md](../docs/02_Архитектура/Безопасность.md) (пункт уже есть, расширяем с конкретикой по эндпоинтам).

Out of scope: реализация admin UI для управления ролями (это `editor-ui` отдельная задача); структура аудит-таблиц в БД (топик `audit.logs` потребляется отдельным сервисом, в эту спеку не входит).

Зависимости: 0024 (shared/authctx → JWT валидация уже есть), 0029, 0030, 0031, 0033.

## Context

- Безопасность [docs/02_Архитектура/Безопасность.md](../docs/02_Архитектура/Безопасность.md):
  - `admin` — полный доступ.
  - `engineer` — `editor-ui` (write-config).
  - `operator` — read в `ms-viewer`, квитирование тревог.
- ms-auth кладёт массив `roles[]` в JWT (см. 0021/0022). `shared/authctx` (0024) парсит JWT и пробрасывает `Principal{Subject, Roles, ...}` в `request.Context()`.
- Kafka топик `audit.logs` — упомянут в [docs/02_Архитектура/Хранилища/Kafka.md](../docs/02_Архитектура/Хранилища/Kafka.md). Producer контракт фиксируется здесь (потребитель — будущий audit-сервис или внешний SIEM).

## Interface

### Ролевая модель (фиксируется в `Безопасность.md`)

| Роль | Доступ |
|---|---|
| `operator` | read всех viewer-эндпоинтов; квитирование тревог; WS подписки. |
| `engineer` | то же, что `operator`, плюс read диагностических эндпоинтов (`/api/notifier/chats` и т.п.). |
| `admin`    | всё, что `engineer`, плюс будущие admin-эндпоинты. |

ms-viewer **не имеет** write-эндпоинтов конфигурации (это территория ms-editor). Ack — единственный «write» в operator-домене.

### Per-endpoint RBAC

| Endpoint | Method | Required roles |
|---|---|---|
| `/healthz`, `/readyz` | GET | none (public) |
| `/api/trends/*` | GET | any of [`operator`, `engineer`, `admin`] |
| `/api/tags*` | GET | any of [`operator`, `engineer`, `admin`] |
| `/api/objects/{id}/diagrams` | GET | any of [`operator`, `engineer`, `admin`] |
| `/api/diagrams/{id}` | GET | any of [`operator`, `engineer`, `admin`] |
| `/api/diagrams/{id}/snapshot` | GET | any of [`operator`, `engineer`, `admin`] |
| `/api/alarms` | GET | any of [`operator`, `engineer`, `admin`] |
| `/api/alarms/{id}` | GET | any of [`operator`, `engineer`, `admin`] |
| `/api/alarms/{id}/acknowledge` | POST | any of [`operator`, `admin`] |
| `/api/notifier/chats` | GET | any of [`engineer`, `admin`] |
| `/api/ws` | GET (upgrade) | any of [`operator`, `engineer`, `admin`] |

Отсутствие требуемой роли → 403 `/errors/auth/forbidden`.

### `RequireRole` / `RequireAnyRole`

```go
func RequireAnyRole(roles ...string) func(http.Handler) http.Handler {
    return func(next http.Handler) http.Handler {
        return http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
            principal, ok := authctx.PrincipalFromContext(r.Context())
            if !ok {
                writeProblem(w, 401, "/errors/auth/invalid-token", "missing principal")
                return
            }
            for _, required := range roles {
                if slices.Contains(principal.Roles, required) {
                    next.ServeHTTP(w, r)
                    return
                }
            }
            writeProblem(w, 403, "/errors/auth/forbidden", fmt.Sprintf("required any of: %v", roles))
        })
    }
}
```

`RequireRole(role)` = `RequireAnyRole(role)`. Cтавится **после** `RequireAuth`.

### WS RBAC

При upgrade — `RequireAuth` + `RequireAnyRole`. При `subscribe`-frame:
- `tag:<id>`, `object:<id>`, `diagram:<id>` — для `operator+engineer+admin` всё открыто (нет per-object permissions в MVP). Если в будущем появятся ACL «оператор видит только свои объекты» — точка расширения здесь.
- `alarms` — то же (без фильтрации по объекту).

В этой спеке per-object ACL **не реализуется**, оставляем точку расширения (комментарий-TODO в `realtime/rbac.go`).

### Audit log payload

Kafka topic `audit.logs`, JSON, key = `actor_id`:

```json
{
  "v": 1,
  "ts": "2026-04-25T10:00:00.123Z",
  "service": "ms-viewer",
  "actor_id": "uuid",
  "actor_username": "operator-1",
  "actor_roles": ["operator"],
  "action": "alarm.acknowledged",
  "target": { "type": "alarm", "id": "<tag_id>", "state": "hi" },
  "details": { "note": "checked", "request_id": "req-abc-123" },
  "result": "success",
  "ip": "10.0.0.5",
  "user_agent": "Mozilla/..."
}
```

### Список действий для аудита из ms-viewer

| `action` | Когда |
|---|---|
| `ws.connected` | upgrade на /api/ws успешен |
| `ws.disconnected` | соединение закрыто (с полем `details.duration_ms`, `details.close_code`) |
| `diagram.opened` | `GET /api/diagrams/{id}` (target: `{type:"diagram", id, name}`) |
| `alarm.acknowledged` | `POST /api/alarms/{id}/acknowledge` |
| `alarm.cleared` | engine cleared в OK (actor_id=null, actor_username="system") |
| `alarm.raised` | engine raised (system) |
| `notifier.dispatched` | сообщение в Telegram отправлено (system) |
| `auth.forbidden` | 403 на любом эндпоинте (полезно для детектирования abuse) |

`alarm.raised`/`alarm.cleared` в audit — оптимально для ретроспективы (хотя это и есть в `alarms.events`, но audit — единый поток для SIEM).

### `AuditUseCase.Record`

```go
type AuditEvent struct {
    Action    string
    Target    AuditTarget
    Details   map[string]any
    Result    string  // "success" | "failure"
}

func (uc *AuditUseCase) Record(ctx context.Context, ev AuditEvent)
```

Поведение:
1. Извлечь `Principal` из ctx; для system-событий (engine, notifier) принимать nil, заполнять `actor_username = "system"`.
2. Дополнить `request_id`, `ip`, `user_agent` из middleware-context.
3. Сериализовать → положить в буферный канал producer’а.
4. Producer асинхронно пишет в Kafka. На `chan` full — drop-oldest + лог `audit.dropped`.

Метод **не возвращает ошибку** — аудит не должен ронять основной flow.

### request_id middleware

В `internal/api/http/middleware.go` — generate UUIDv4 на каждый запрос, кладём в `Context`, ответе `X-Request-Id`. Уже желательно по 0029, здесь подтверждаем.

## Constraints

- RBAC применяется **после** `RequireAuth`. Порядок middleware: `recover → request_log → request_id → RequireAuth → RequireRole → handler`.
- 403 не различается между «нет роли» и «роль не та» — единый `forbidden`-код. Detail-поле может уточнить, но без раскрытия списка ролей системы.
- Системные действия (engine, notifier, scheduler) пишутся в audit с `actor_id=null, actor_username="system"`. На consumer-стороне это легко отфильтровать.
- Audit producer — отдельная горутина с локальным буфером (`AuditBufferSize`); полная очередь → drop-oldest. Это лучше, чем блокировать handler ради аудита.
- При недоступности Kafka — events не теряются мгновенно (буфер на ~1000 событий), но при длительной недоступности — drop. На production-стенде — мониторить метрики `audit.dropped_total`.
- Логи в slog **дублируют** ключевые audit-events (минимум `action`, `actor_id`, `result`) — на случай, если Kafka в дауне. Это не «настоящий аудит», но как fallback пригодно.
- Audit payload — стабильный контракт. Добавление полей — допустимо (forward-compat); удаление/переименование — major-bump `v`.
- Тестирование: integration-тесты с testcontainers пока вне scope; unit-тесты на:
  - middleware RBAC (входной Principal + ожидаемый код).
  - audit_usecase: payload-format, fallback на nil-Principal, drop-on-full-buffer.
- Не публиковать audit в один топик с `alarms.events` — конфликт partitioning по ключу.
- Топик `audit.logs` — partitioned by `actor_id`, retention ≥ 90d (конфигурация — DevOps).
- Соответствие GDPR/PII: `details` НЕ должен содержать пароли, токены, raw JWT.

## Verify

### RBAC

- `go test ./internal/api/http/rbac_test.go` — все таблицы зелёные.
- Запрос `GET /api/trends/<id>` с JWT без `roles` → 403 `/errors/auth/forbidden`.
- С `roles: ["operator"]` → 200.
- С `roles: ["operator"]` POST `/api/alarms/<id>/acknowledge` → 200.
- С `roles: ["engineer"]` POST acknowledge → 403 (engineer не имеет права квитировать).
- С `roles: ["admin"]` любой эндпоинт → 200.
- WS upgrade без ролей → 401 (или 403 после auth) — в зависимости от того, где ловит middleware; задокументировать.

### Audit

- В Kafka `audit.logs` после `POST /api/alarms/<id>/acknowledge`:
  ```json
  {"v":1,"ts":"...","service":"ms-viewer","actor_id":"uuid","actor_username":"operator-1","actor_roles":["operator"],"action":"alarm.acknowledged","target":{"type":"alarm","id":"<tag_id>","state":"hi"},"details":{"note":"...","request_id":"..."},"result":"success",...}
  ```
- WS connect/disconnect фиксируется: видно `ws.connected` на upgrade, `ws.disconnected` с `duration_ms` на close.
- Engine raised: система пишет `alarm.raised` без actor_id; consumer видит `actor_username:"system"`.
- При Kafka-down (3 минуты): метрика `audit.dropped_total` растёт; при возврате — буфер спустошён, новые события идут.
- На любой 403 — событие `auth.forbidden` в audit.
- Каждый аудит-event имеет уникальный `request_id` (для cross-service tracing с editor/auth).
- Шумных audit-event не более 1 на запрос (а не 2 от двух middleware).
