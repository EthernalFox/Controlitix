# 0025: ms-editor — Bulk upsert фигур (`PUT /diagrams/{id}/figures`)

## Scope

`ms-editor/internal/` — domain, usecase, infrastructure/repository, api/http.
Контракт: `docs/04_API/ms-editor.md` (секция «Bulk upsert фигур»).

## Context

Канвас `editor-ui` (спека 0011) сохраняет мнемосхему целиком: после правок нужно привести состав фигур к текущему состоянию редактора. Поэкземплярные `POST/PATCH/DELETE` не подходят — при массовых правках получается N HTTP-запросов, нет атомарности (частичное сохранение при разрыве связи), сложно реализовать autosave.

Дополнительно: текущий `PostgresRepository.CreateFigures` — заглушка (`return nil, domain.ErrNotImplemented` в [postgres_repository.go:268-274](../ms-editor/internal/infrastructure/repository/postgres_repository.go#L268-L274)). То есть существующий `POST /diagrams/{id}/figures` отвечает 500 и фигуры в БД фактически не создаются. Эта спека закрывает и этот пробел.

## Interface

### HTTP

```
PUT /diagrams/{diagramId}/figures
Content-Type: application/json

{
  "figures": [
    { "id": "a1b2...", "type": "rect",   "tag_id": null,     "params": { "x":10, "y":20, "w":100, "h":40 } },
    {                    "type": "circle","tag_id": "t-123", "params": { "cx":50, "cy":50, "r":20 } }
  ]
}
```

Ответ `200 OK`:

```json
{
  "figures": [
    { "id":"a1b2...", "diagram_id":"d-1", "type":"rect",   "tag_id":null,     "params":{...}, "created_at":"...", "updated_at":"..." },
    { "id":"c3d4...", "diagram_id":"d-1", "type":"circle", "tag_id":"t-123",  "params":{...}, "created_at":"...", "updated_at":"..." }
  ],

}
```

### UseCase

```go
// usecase/figure_usecase.go

func (uc *FigureUseCase) BulkUpsertFigures(
    ctx context.Context,
    diagramID string,
    items []domain.FigureBulkItem,
) (domain.FigureBulkResult, error)
```

Поведение:
1. Валидация входа: `diagramID` не пуст, `items` — допускается пустой список (эквивалент «удалить все фигуры мнемосхемы»); каждый `FigureType` — через `domain.ParseFigureType`.
2. Вызов `figureRepository.BulkUpsertFigures`.
3. После успешного возврата — публикация `domain.ConfigChangedEvent` по одному на каждую затронутую фигуру (created/updated/deleted). Определение «затронутости»:
   - created — новые `id` из результата;
   - updated — `id` присутствовал в запросе и в итоговом списке;
   - deleted — `id` был в БД до операции, но отсутствует в итоговом списке (репозиторий возвращает список `deleted_ids` в `FigureBulkResult` — см. ниже).

Ошибки публикации — логируются через `slog`, транзакция не откатывается.

### Repository (транзакция)

Внутри одной БД-транзакции:

1. `SELECT id FROM public.figures WHERE diagram_id = $1 AND deleted_at IS NULL FOR UPDATE` — захват текущего состава.
2. Для каждого входного элемента:
   - с `id`: проверить, что `id` есть в множестве из шага 1 (иначе → `domain.ErrNotFound` с деталью «figure {id} does not belong to diagram {diagramID}»); выполнить `UPDATE figures SET type=$..., tag_id=$..., updated_at=now() WHERE id=$...`; `INSERT ... ON CONFLICT (figure_id) DO UPDATE SET params=$..., updated_at=now()` на `figure_params`.
   - без `id`: `INSERT INTO figures (diagram_id, type, tag_id) VALUES (...) RETURNING id`; `INSERT INTO figure_params (figure_id, params) VALUES (...)`.
3. Множество `id_в_БД \ id_в_запросе` → `UPDATE figures SET deleted_at = now(), updated_at = now() WHERE id = ANY($...)`; `UPDATE figure_params SET deleted_at = now() WHERE figure_id = ANY($...)`.
4. `SELECT` по итоговому составу мнемосхемы с join `figure_params` → возвращается `[]Figure` в порядке тела запроса.
5. Commit. `FigureBulkResult.Created/Updated/Deleted` — счётчики; `Figures` — итог.

Расширить `FigureBulkResult` служебным полем (не в API-ответе):

```go
type FigureBulkResult struct {
    Figures    []Figure
    Created    int
    Updated    int
    Deleted    int
    CreatedIDs []string // для publishFigureEvent в usecase
    UpdatedIDs []string
    DeletedIDs []string
}
```

### Router

В `handleDiagrams` при совпадении сегмента `figures`:
- `POST` → существующий `createFigures` (оставить без изменений).
- `PUT` → новый `bulkUpsertFigures(w, r, diagramID)`.
- `GET` → существующий `listFiguresByDiagram`.
- Прочее → `405 Method Not Allowed` через `writeMethodNotAllowed` (используется в сервисе).

## Constraints

- Вся операция — в одной транзакции через существующий `repository.executor(ctx)`/`WithTransaction` паттерн (следовать тому, как сделано в `DeleteMonitoringObject`/`DeleteDevice` — см. существующий код).
- Не нарушать Clean Architecture: валидация `FigureType`, формата `params` и «все ли `id` в теле уникальны» — в usecase; SQL — только в `infrastructure/repository`; парсинг JSON и коды ответов — только в `api/http`.
- Не добавлять новые внешние зависимости.
- Ошибки формируются через существующий RFC 7807 (`writeDomainError` / `*ValidationError` из 0007). Дубли `id` в теле → 422 `validation-error` с полем `figures[i].id`; `id` из другой мнемосхемы → 404 `not-found`.
- Cобытия `config.changed` публикуются **после** `tx.Commit()`, не внутри транзакции.
- При `len(items) == 0` — допустимо, операция soft-delete всех фигур мнемосхемы. Не возвращать 400.
- Не трогать существующие `POST /diagrams/{id}/figures`, `PATCH /figures/{id}`, `DELETE /figures/{id}` — их контракт сохраняется.
- `CreateFigures` (закрытие заглушки) — реализовать через ту же транзакционную логику, но без фазы delete-missing: тоже SELECT `FOR UPDATE`? не нужен — достаточно простого INSERT по списку.
- Не использовать `ON CONFLICT (id)` для `UPDATE` в figures: идентификаторы поступают от клиента, но они должны быть заранее созданными; если клиент пришёл с неизвестным `id` — это 404, а не «вставить с этим id».
- Запретить `tag_id`, указывающий на несуществующий/удалённый тег — либо отложить проверку на FK (текущий `tag_id` в `figures` не имеет FK — см. `000001_init.sql`; проверку добавлять в рамках этой спеки **не надо**, это отдельная задача). Ограничиться форматом UUID.

## Verify

- `go build ./...` — без ошибок.
- `go test ./ms-editor/...` — unit-тесты проходят.
- `POST /diagrams/{id}/figures` с валидным телом — возвращает 201 и реально создаёт записи в БД (проверка закрытия заглушки `ErrNotImplemented`).
- `PUT /diagrams/{id}/figures` с пустым `figures: []` — soft-deletes все фигуры мнемосхемы, отвечает 200, `summary.deleted == N`.
- `PUT /diagrams/{id}/figures` со смесью (часть с `id` — существующие, часть без `id` — новые, часть существующих отсутствует) — атомарно обновляет/создаёт/soft-delete, счётчики в `summary` совпадают, порядок `figures` в ответе совпадает с порядком в запросе.
- `PUT` с `id` из другой мнемосхемы — отвечает 404, **ничего в БД не меняет** (проверить через `GET /diagrams/{id}/figures` до и после).
- `PUT` с дублем `id` в теле — 422, указан `field: "figures[i].id"`.
- `PUT` с `type: "unknown"` — 422.
- По результату успешного `PUT` на Kafka-топик `config.changed` попали события по одному на каждую created/updated/deleted фигуру.
- SQL в репозитории — один SELECT `FOR UPDATE`, пакетные `UPDATE ... WHERE id = ANY(...)` для delete-фазы (не N отдельных запросов).
- OpenAPI `swagger/openapi.yaml` — добавлен путь `put`, примеры запроса/ответа соответствуют DTO.
