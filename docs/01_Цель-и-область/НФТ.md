# Нефункциональные требования (MVP)

Документ фиксирует количественные характеристики, на которые проектируется первая версия Controlitix. Все значения указаны для **одной инсталляции** (один физический хост на объект, self-hosted).

## Контекст первой инсталляции

- **Заказчик:** предприятие с двумя ЦОДами.
- **Объекты мониторинга:** 3 на ЦОД (2 серверных + 1 помещение ИБП), итого **6 объектов**.
- **Инсталляций:** 2 (по одной на ЦОД).
- **Развёртывание:** один физический хост на объект, Docker Compose.

## Масштаб одной инсталляции

| Параметр | Типовое значение | Проектный потолок |
|---|---|---|
| Объектов мониторинга | 3 | 10 |
| Устройств на объект | ~100 | 250 |
| Тегов на устройство | ~10 | 30 |
| Тегов всего | ~2 500 | ~7 500 |
| Мнемосхем | 3–10 | 50 |
| Фигур на схеме | до 200 | 500 |
| Одновременных операторов | 3–5 | 20 |

**Распределение устройств по протоколам:**

- **60%** — Modbus RTU (электросчётчики).
- **20%** — датчики температуры (через Modbus / 1-Wire / сухой контакт).
- **20%** — SNMP (ДГУ, кондиционеры, ИБП).

## Частота опроса (scan rate)

| Тип тега | Частота опроса | Комментарий |
|---|---|---|
| Электрические параметры | 1 Гц (1 с) | Счётчики, токи, напряжения |
| Состояния (SNMP traps/poll) | 1 Гц | ДГУ, ИБП, кондиционеры |
| Температура | 1/60 Гц (60 с) | Инертная величина |
| Health-check устройства | 1/10 Гц (10 с) | Проверка «живости» |

**Расчётный поток значений:**

- ~2 000 тегов × 1 Гц = 2 000 значений/сек.
- ~500 тегов × 1/60 Гц ≈ 8 значений/сек.
- **Итого: ~2 000–2 100 значений/сек** (пик для полностью заполненной инсталляции).

## Историзация

- **Глубина хранения raw-значений:** 1 год.
- **Downsampling:**
  - 0–30 дней: raw.
  - 30–365 дней: 1-минутные агрегаты (min/max/avg/count).
- **Технология:** TimescaleDB (PostgreSQL extension), hypertables + continuous aggregates + retention policies.
- **Целевой объём на год:** ориентировочно ~60 ГБ на инсталляцию (до сжатия Timescale), оценка уточняется на пилоте.

## Задержки (realtime-контур)

| Метрика | Цель MVP |
|---|---|
| От опроса устройства до появления значения в Viewer (WS) | ≤ 2 с (p95) |
| От срабатывания условия до события тревоги | ≤ 3 с (p95) |
| От события тревоги до сообщения в Telegram | ≤ 5 с (p95) |
| Загрузка мнемосхемы в Viewer | ≤ 1 с (p95, 200 фигур) |
| Загрузка тренда (1 час, 10 тегов) | ≤ 1 с (p95) |
| Загрузка тренда (1 месяц, 10 тегов) | ≤ 3 с (p95) |

## Производительность редактора (editor-ui)

- **Рендер холста:** ~60 fps при ≥ 500 фигурах (Konva, батч-обновления, throttle/RAF).
- **Undo/Redo:** ≤ 10 мс на шаг при типовых изменениях, история ≥ 50 шагов.
- **Автосохранение черновика:** каждые ~5 с при наличии несохранённых изменений (localStorage/IndexedDB).
- **Upsert фигур через ms-editor:** < 100 мс при типовых размерах схемы.
- **CRUD устройств/тегов через ms-editor:** ≤ 100 мс.

## Доступность (SLA)

- **Целевая доступность:** 99.9% в год (≈ 8 ч 46 мин простоя/год).
- **Окна обслуживания:** допустимы (мониторинг дублируется у заказчика на стороне).
- **RPO (допустимая потеря данных):** ≤ 5 минут для исторических значений.
- **RTO (целевое время восстановления):** ≤ 30 минут на Docker Compose-инсталляции.

## Требования к железу (на один хост/объект)

Ориентировочные минимумы для типовой нагрузки (уточнить на пилоте):

| Ресурс | Минимум | Рекомендовано |
|---|---|---|
| CPU | 4 vCPU | 8 vCPU |
| RAM | 8 ГБ | 16 ГБ |
| Диск (системный) | 50 ГБ SSD | 100 ГБ SSD |
| Диск (данные PG/Timescale) | 100 ГБ SSD | 250 ГБ SSD |
| Сеть | 1 Гбит/с | 1 Гбит/с |

Для SNMP/Modbus RTU — дополнительно USB-RS485 конвертеры или последовательные интерфейсы на хосте.

## Сетевые требования

- **Контур:** внутренняя сеть организации, без внешнего доступа.
- **Порты наружу:** только Nginx (HTTPS 443 внутри LAN), доступ к Telegram Bot API (исходящий, TLS 443).
- **Межсервисное взаимодействие:** внутри Docker Compose по внутренней сети, без mTLS (см. ADR-0008).

## Безопасность (MVP)

- Единая точка входа — Nginx (TLS-термирование опционально, сертификат самоподписанный или корпоративный).
- Аутентификация пользователей — `ms-auth`, три роли (admin / engineer / operator), без per-object RBAC.
- Межсервисная аутентификация — технологические учётные записи (ТУЗ) с секретами в env.
- Шифрование at rest — **не требуется** (решение заказчика).
- Персональные данные — **не обрабатываются**.
- Secrets management — переменные окружения (`.env`).

## Observability

- **Мониторинг самой платформы:** Zabbix agent на хосте (решение заказчика, используется существующая инфраструктура).
- **Health/readiness/liveness endpoints:** обязательны для всех микросервисов.
- **Логи:** структурированные (JSON), выводятся в stdout, собираются Docker/хостом.
- **Собственные бизнес-метрики и SLO:** вне MVP.

## Наблюдаемые ограничения MVP

- Нет per-object RBAC (все залогиненные с ролью видят всё).
- Нет версионирования схем и API.
- Нет экспорта истории (CSV/PDF).
- Нет эскалаций тревог.
- Уведомления — только Telegram.
- Нет шифрования at rest.
- Нет мобильных клиентов.
- Нет SSO/LDAP/AD.
