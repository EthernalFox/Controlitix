# 0030: Realtime — WebSocket-контракт между ms-viewer и viewer-ui

## Scope

Полный realtime-канал «значения тегов в реальном времени»:

1. Backend (`ms-viewer/internal/`): WebSocket-эндпоинт `/api/ws`, fan-out из Kafka `tags.values`, протокол subscribe/unsubscribe, авторизация по JWT.
2. Frontend (`viewer-ui/src/`): клиент `shared/modules/realtime/`, store подписок, интеграция в `pages/TrendsPage` (live-tail к графику) и заглушка-API для будущего `pages/DiagramPage`.
3. Документация контракта в `docs/04_API/ms-viewer-ws.md`.

Out of scope: alarms-стрим (`alarms.events` через WS — отдельная спека), деградация до polling (для MVP клиент просто показывает «соединение потеряно» и реконнектит).

## Interface

### Protocol (JSON over WS)

Все сообщения — JSON, поле `t` (type) — обязательное. Имена полей — snake_case (как в REST).

#### Client → Server

```json
{ "t": "subscribe",   "topics": ["tag:UUID-1", "tag:UUID-2"] }
{ "t": "unsubscribe", "topics": ["tag:UUID-1"] }
{ "t": "ping" }
```

`topics` — список строк формата `tag:<uuid>` (заготовка под будущие `object:<uuid>`, `diagram:<uuid>`, `alarms`). В этом спеке поддерживаем только `tag:<uuid>`. Незнакомый префикс → `error`-ответ, остальные топики из той же команды обрабатываются.

#### Server → Client

```json
{ "t": "welcome", "session_id": "...", "server_time": "2026-04-25T10:00:00Z", "limits": { "max_subscriptions": 200, "debounce_ms": 100 } }

{ "t": "subscribed",   "topics": ["tag:UUID-1", "tag:UUID-2"] }
{ "t": "unsubscribed", "topics": ["tag:UUID-1"] }

{ "t": "value", "tag_id": "UUID-1", "ts": "2026-04-25T10:00:00.123Z", "v": 75.4, "q": "ok" }

{ "t": "snapshot", "tag_id": "UUID-1", "ts": "2026-04-25T10:00:00Z", "v": 75.4, "q": "ok", "reason": "subscribe" | "heartbeat" }

{ "t": "pong" }

{ "t": "error", "code": "limit-exceeded" | "invalid-topic" | "auth-required" | "unauthorized" | "rate-limited", "detail": "human-readable", "topics": ["..."] }
```

Поведение:
- На `subscribe` — сервер сразу отправляет `subscribed`, затем по каждому теге `snapshot` с последним значением из Redis-кэша (если есть; нет — пропуск).
- В фоне — `value`-сообщения по мере поступления `tags.values` из Kafka, не чаще `WSDebounceMs` на тег.
- Если по тегу не было новых значений за 30 секунд — сервер шлёт `snapshot { reason: "heartbeat" }` (тот же что был). Клиент использует это как «связь жива».
- Ping/pong — каждые `WSPingIntervalSec`. Если за `WSPongTimeoutSec` нет pong — сервер закрывает соединение с кодом 1001.

### Авторизация

WS endpoint `GET /api/ws`:
- Клиент передаёт access-токен в **query-параметре** `?access_token=<jwt>` (cookie не работают надёжно с WS в браузере; Sec-WebSocket-Protocol можно использовать как fallback, но для MVP — query).
- Сервер валидирует токен через тот же `RequireAuth` (audience = user). Невалидный → 401 до апгрейда; пропавший — 1008 close после апгрейда.
- Принудительный пере-auth при `refresh` access-токена: клиент закрывает текущий WS и открывает новый с новым токеном (см. § Frontend integration).

### Backend — fan-out pipeline

```
Kafka tags.values
   ↓
TagValueHandler.Handle (как в 0029)
   ├──→ IngestUseCase.IngestTagValue (history + Redis)
   └──→ Dispatcher.Publish(record)
            ↓
        Hub.Publish(tag_id, payload)
            ↓
        Debouncer per (tag_id, connection)
            ↓
        Connection.outbox <- payload     (если очередь полная — drop oldest, лог warn)
            ↓
        WS frame
```

Замечания:
- Hub держит `map[tagID]map[*Connection]struct{}` под `sync.RWMutex`. Для масштаба MVP (≤ 1000 одновременных клиентов) этого достаточно. Горизонтальное масштабирование (несколько ms-viewer-инстансов с Redis pub/sub) — отдельная спека.
- Debouncer работает per-(connection, tag): у каждого соединения свой таймер на тег. Это проще, чем глобальный debounce; и позволяет редким клиентам получать данные с минимальной задержкой, а медленным — не задыхаться.
- Backpressure: если `outbox` соединения переполнен (`WSWriteBufferSize`), drop **oldest** (старые точки клиенту уже неактуальны), счётчик `realtime.dropped_total{reason="outbox_full"}` через slog/metrics.

### Frontend — `RealtimeClient`

```ts
// shared/modules/realtime/client.ts
export interface RealtimeClient {
  start(): void;          // открыть соединение
  stop(): void;           // graceful close (1000)
  subscribe(topics: string[]): void;   // refcount внутри
  unsubscribe(topics: string[]): void;
  on<T extends ServerMessage["t"]>(type: T, handler: (msg: ServerMessage & { t: T }) => void): () => void;
}
```

Состояние:
- `connecting` → `open` (после welcome) → `reconnecting` → `open` → ... → `closed`.
- Reconnect — backoff `min(30s, 1s * 2^attempt)` + jitter ±200ms.
- При reconnect: повторно отправить `subscribe` на все топики из локального refcount-store.

Refcounting:
- `subscribe(["tag:A"])` 3 раза подряд → отправлен один `subscribe` с `tag:A`, refcount A = 3.
- `unsubscribe(["tag:A"])` — decrement; при 0 — отправить `unsubscribe` на сервер.
- При `stop()` или auth-смене — refcount сбрасывается, на сервер отправляем `unsubscribe` (best-effort) и закрываем.

### Frontend — `useTagSubscription`

```ts
useTagSubscription(
  tagIds: string[],
  onValue: (msg: { tag_id: string; ts: string; v: number | null; q: Quality; isSnapshot: boolean }) => void,
);
```

- Hook авто-подписывается при mount, обновляет подписки при изменении `tagIds`, отписывается при unmount.
- Снапшоты и live-values приходят в один callback с флагом `isSnapshot`.
- Все ошибки `error` от сервера логируются (не пробрасываются в callback).

### Интеграция в TrendsPage

После завершения исторической загрузки и при условии «range.preset ∈ {5m, 1h, 6h, 24h}»:
1. Подписаться на `[tag:<id1>, tag:<id2>, ...]`.
2. На каждый `value` (не `snapshot`) — `appendLivePoint(tagId, { ts, v, q })`.
3. `appendLivePoint` обрезает точки старше `range.from`, чтобы массив не рос бесконечно.
4. Chart.js `data` обновляется через `data` prop (Chart.js diff’ит и сам делает плавную дорисовку).
5. На preset’ах `7d`/`30d`/`custom` — live-tail **не** включается (плотность не та).

Polling 15s из 0028 при включённом live-tail отключается (флаг в store: `liveTailActive: boolean`).

### `RealtimeStatus`

В шапке точка-индикатор:

| Статус | Цвет | Tooltip |
|---|---|---|
| `open` | зелёный (alarm-ok) | «Realtime подключён» |
| `connecting` / `reconnecting` | янтарный (alarm-warn) | «Восстанавливаем соединение…» |
| `closed` | серый (alarm-comm) | «Realtime отключён» |

Клик по индикатору — открывает popover с количеством активных подписок и кнопкой «Переподключить».

## Constraints

### Общие

- Контракт WS — single source of truth: `docs/04_API/ms-viewer-ws.md`. Любое расширение протокола = доработать документ.
- Все ts/времена — UTC, RFC3339.
- Качество (`q`) — те же 8 значений, что в REST.
- Никаких бинарных кадров — только JSON-text. Это упрощает отладку; протокол можно проапгрейдить позже.

### Backend

- WebSocket-библиотека: `nhooyr.io/websocket` (она же `coder/websocket` после форка) — единственная зависимость, без `gorilla/websocket` (deprecated).
- WS-handler не должен блокировать reader/writer-goroutine на работе с БД/Redis. Любая работа = уйти в IngestUseCase, не в WS-горутины.
- Никаких глобальных `var` Hub — DI через main.go.
- Защита: `WSMaxConnectionsPerUser` (по `Principal.Subject`); при превышении — закрыть самое старое соединение.
- Защита: `WSMaxSubscriptionsPerConn`; при попытке `subscribe` сверх — `error: "limit-exceeded"`, лишние топики не подписываются.
- Любая ошибка апгрейда → 401/400 до WS, после — close-frame (1008 unauthorized, 1011 internal).
- Логи: `connection.opened`, `connection.closed{reason,code,duration_ms}`, `subscribe{topics}`, `dropped{tag_id,reason}`. Без значения тега в логах (PII-нейтрально, но шум).
- Конкурентный доступ к `Hub` — `sync.RWMutex` на чтение (`Publish` — много читателей одной map); запись (`Subscribe`/`Unsubscribe`) — write-lock, но редкая.

### Frontend

- **Один** `RealtimeClient` на приложение. Singleton, инициализация в `app/App.tsx` после auth-bootstrap.
- WS подключается **только** в статусе `authenticated`. На `unauthenticated` — клиент закрыт.
- При обновлении access-токена (proactive refresh из 0027) клиент:
  1. Сохраняет список текущих топиков.
  2. Закрывает соединение (1000).
  3. Открывает новое с свежим токеном.
  4. Восстанавливает подписки.
- Reconnect-backoff не должен мешать handle’у `stop()` — на manual stop соединение не пытается переподключиться.
- Обработчик `message` — pure, без побочных эффектов на UI напрямую. Всё через store + hooks.
- Не использовать `socket.io` / `centrifuge-js` / другие надстройки. Только нативный `WebSocket`.
- `useTagSubscription` не должен дёргать `subscribe` при каждом ре-рендере — мемоизация по `tagIds.join(",")`.
- live-tail на TrendsPage не должен вызывать перерисовку всего React-дерева: обновление точек идёт через imperative API Chart.js (через `data` prop) или через узкий subscriber на `seriesByTag[id]`.
- Никаких прямых импортов `@mantine/core` в `widgets/RealtimeStatus` — только через фасад `shared/ui/components`.

## Verify

### Backend

- `go build ./... && go test ./internal/realtime/...` — зелёные.
- `nc localhost 8084` (или wscat) с валидным `?access_token=...` → `welcome`-фрейм.
- Без токена → 401 на handshake.
- `subscribe { topics: ["tag:<id>"] }` → ответ `subscribed` + сразу `snapshot` (если в Redis есть значение).
- Опубликовать в `tags.values` 10 значений за 1 секунду на один `tag_id` → клиент получает не больше `1000ms / WSDebounceMs = ~10` `value`-фреймов (с `WSDebounceMs=100`); последний всегда самый свежий.
- Отсутствие изменений 30 секунд → клиент получил `snapshot { reason: "heartbeat" }`.
- Не отвечать pong 35s → сервер закрывает соединение, в логе `connection.closed{reason="pong_timeout"}`.
- Открыть 6-е соединение от того же пользователя при `WSMaxConnectionsPerUser=5` → самое старое получает close-frame, новое работает.
- Подписаться на 250 тегов при `WSMaxSubscriptionsPerConn=200` → `error: "limit-exceeded"`, реально подписано 200.
- Перезапуск ms-viewer (graceful) → клиенты получили close 1001/1012, реконнектятся, подписки восстанавливаются.
- `go test -race ./internal/realtime/...` — без race-warning.

### Frontend

- `npm run build && npm run lint` — без ошибок.
- DevTools → Network → WS frames: `welcome` после логина, `subscribe` после открытия `/trends` с одним выбранным тегом, `value`-фреймы появляются.
- На `/trends` preset `5m` с одним тегом — после полной загрузки исторического тренда новые точки доезжают на график без лагов; polling 15s **не** отправляется (отключён, см. constraint).
- Switch preset с `5m` на `30d` — live-tail отключается, polling тоже отключён, обновление графика — только при ручном refresh.
- Принудительный refresh access-токена (имитация: сократить TTL до 60s) → в Network видно `WS close 1000` → новый `WS upgrade` с новым токеном → `subscribe` восстанавливает все топики автоматически.
- Сетевой провал (`offline` в DevTools на 5s) → `RealtimeStatus` становится янтарным; после восстановления — зелёным; график догоняет (получает `snapshot` после reconnect).
- Logout → `WS close 1000`, нет фоновых reconnect-попыток (проверить в DevTools, что нет повторных WS-handshake’ов).
- Подписаться на 6 тегов → в WS-frames ровно один `subscribe` с 6 топиками (батч), не 6 отдельных.
- Размонтаж `TrendsPage` → `unsubscribe` отправляется по всем топикам страницы; refcount в store обнулён.
