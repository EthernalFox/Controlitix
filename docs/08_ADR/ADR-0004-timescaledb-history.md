# ADR-0004: TimescaleDB для архива значений тегов

- Статус: accepted
- Дата: 2026-04-15
- Авторы: команда Controlitix

## Контекст

Controlitix должен хранить историю значений тегов в течение 1 года (см. [`НФТ.md`](../01_Цель-и-область/НФТ.md)). Ожидаемый пиковый поток — около 2 000–2 100 значений в секунду на инсталляцию. Это даёт:

- ~175 млн точек в сутки;
- ~63 млрд raw-точек в год.

Обычная таблица PostgreSQL без партиционирования на таких объёмах теряет производительность запросов по диапазонам времени и становится неуправляемой по размеру (индексы, VACUUM, retention).

Viewer должен выдавать тренды на окнах 5 минут, 1 час и 1 месяц. Без downsampling запрос за месяц по 10 тегам поднимает миллионы точек и не укладывается в целевые 3 секунды (p95).

## Рассмотренные варианты

1. **Обычный PostgreSQL + партиции по времени + ручной downsampling** — бесплатно и без зависимостей, но вся логика retention/downsampling ложится на `ms-viewer`: нужно писать cron-задачи, агрегаторы, менеджер партиций. Много кода, много мест для ошибок.
2. **TimescaleDB как extension к PostgreSQL** — одна extension, остаётся то же подключение и те же инструменты. Даёт hypertables (автоматические партиции), continuous aggregates (автоматический downsampling), retention policies (автоматическая очистка) и сжатие колоночного типа.
3. **Отдельная TSDB (InfluxDB, ClickHouse, VictoriaMetrics)** — эффективнее на сверхбольших объёмах, но вводит второе хранилище, второй backup-контур и второй протокол. Для ~2 000 точек/с избыточно.

## Решение

Используем **TimescaleDB как расширение PostgreSQL**. Это единственная БД платформы — отдельный инстанс не поднимаем, Timescale подключается как extension к основному PostgreSQL.

**Архитектура хранения истории:**

- Схема `history`.
- Таблица `history.tag_values_raw` — hypertable, chunk_interval = 1 день.
  - Колонки: `ts timestamptz`, `tag_id uuid`, `value_double double precision`, `value_bool boolean`, `value_text text`, `quality smallint`.
  - Индексы: по `(tag_id, ts DESC)` и по `ts DESC`.
- **Continuous aggregate** `history.tag_values_1m` — 1-минутные агрегаты (min/max/avg/count/last).
- **Retention policies:**
  - `tag_values_raw` — 30 дней.
  - `tag_values_1m` — 365 дней.
- **Compression policy:** включить колоночное сжатие на чанках старше 7 дней для `tag_values_raw`.

**Маршрутизация запросов трендов в `ms-viewer`:**

- Окно ≤ 24 часа → из `tag_values_raw`.
- Окно > 24 часов → из `tag_values_1m`.
- Промежуточные режимы дробления по времени — из continuous aggregate с соответствующей гранулярностью.

## Последствия

**Позитивно:**

- Retention и downsampling — декларативные, без собственного кода в `ms-viewer`.
- Единый backup/restore с основной БД (`pg_dump`/WAL-archive — с учётом ограничений Timescale).
- Запросы по времени быстрые из коробки.
- Колоночное сжатие экономит диск (10–20× на типовых временных рядах).

**Негативно:**

- TimescaleDB — отдельная лицензионная история: community edition свободен, Apache 2 purely community features — ограничены (compression и continuous aggregates в community edition сейчас разрешены, но нужно следить за лицензией на момент релиза). **Зафиксировать в операционной документации требование TSL-соответствия при коммерческом использовании.**
- `pg_dump` не идеально дружит с hypertables; backup-стратегия должна использовать `pg_dump` с `--exclude-table-data` для чанков или специализированные средства TS.
- Миграции через Goose должны учитывать создание hypertables и политик.
