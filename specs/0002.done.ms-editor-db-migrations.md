# 0002: ms-editor — DB migrations: devices, tags, seed data

## Scope

`ms-editor/migrations/`, `ms-editor/agents.md`.

## Context

Phase 2 ms-editor requires tables for devices and tags. Currently only `public` schema exists (migration `000001_init.sql`). This task creates schemas `devices` and `tags`, all tables, reference data, and fixes gaps in existing `public` schema (missing `type` column in `figures`, missing `deleted_at` columns).

Related: `docs/03_Модель-данных/`, `docs/04_API/ms-editor.md`.

Architectural decision: `devices.devices.object_id` is **nullable** (device can exist independently, assigned to object optionally).

## Files

- `ms-editor/migrations/000002_devices_tags_schemas.sql` — **create** (Goose migration)
- `ms-editor/agents.md` — **modify** (update schema ownership section)

## agents.md change

Update the "Purpose" and "Database rules" sections:

**Database rules** — replace the cross-schema FK rule with:
> `ms-editor` owns three schemas: `public`, `devices`, `tags`. Cross-schema FKs between these three are allowed. FKs to schemas owned by other services (e.g., `history`, `alarms`, `auth`) are forbidden.

## Constraints

- Do not modify `000001_init.sql`.
- The migration must be idempotent where possible (`IF NOT EXISTS`, `IF EXISTS`).
- `offset` is a reserved word in PostgreSQL — always quote it as `"offset"`.
- Seed data IDs are auto-generated (`serial`); do not hard-code IDs.

## Review notes

### `tags.tag_params(tag_id)` must be UNIQUE

Spec line 182 and `migrations/000002_devices_tags_schemas.sql:192` create a **non-unique** index:

```sql
CREATE INDEX IF NOT EXISTS tag_params_tag_id_idx ON tags.tag_params (tag_id);
```

But the upsert in `internal/infrastructure/repository/postgres_repository.go:862` uses:

```sql
ON CONFLICT (tag_id) DO UPDATE
```

PostgreSQL requires a UNIQUE or EXCLUSION constraint matching the `ON CONFLICT` target. Without it, every call to `UpsertTagParams` fails at runtime with:

> ERROR: there is no unique or exclusion constraint matching the ON CONFLICT specification

This also matches the intended cardinality: `tag_params` is 1:1 with `tags` (mirroring `devices_params(device_id PRIMARY KEY)`), and `ListTags` uses `LEFT JOIN tags.tag_params` assuming at most one row per tag.

**Fix:** change the index to UNIQUE in both the spec and the migration:

```sql
CREATE UNIQUE INDEX IF NOT EXISTS tag_params_tag_id_uniq ON tags.tag_params (tag_id);
```

(or add a column-level `UNIQUE` to `tag_id`). Update the spec snippet at line 182 accordingly.
