# 0032: ms-viewer — `config.changed` consumer + cache invalidation + push в WS

## Scope

`ms-viewer/internal/`:
- Kafka-консьюмер топика `config.changed`.
- In-memory кэш мета-данных тега (имя, единица, тип данных, device_*) для горячего пути `/api/trends/*`.
- Инвалидация кэша по событиям.
- Server→Client WS-сообщение `config.changed` для viewer-ui (push с просьбой перезагрузить мнемосхему/тренд).

Out of scope: реальная инвалидация HTTP-кэшей в `editor-ui` или браузере (это уже клиентская задача); ETag/`If-None-Match` (отдельная мини-задача).

## Context

`ms-editor` публикует [domain.ConfigChangedEvent](../ms-editor/internal/domain/event.go):

```json
{
  "entity_type": "object | device | tag | diagram | figure",
  "entity_id":   "uuid",
  "operation":   "created | updated | deleted | published | ...",
  "timestamp":   "RFC3339",
  "actor_id":    "uuid|null",
  "payload":     { /* entity snapshot, raw JSON */ }
}
```

Kafka key = `entity_type:entity_id` (см. `ms-editor/internal/infrastructure/kafka/producer.go`).

Сейчас (после 0029/0030/0031):
- `ms-viewer` НЕ читает `config.changed` → если ms-editor переименовал тег, в `/api/trends` всё ещё старое имя пока не перезапустят сервис (метаданные забираются из БД на каждый запрос — мгновенно консистентно, кэша нет).
- `viewer-ui` не узнаёт о публикации новой версии мнемосхемы — оператор видит старую до F5.

Этот спек закрывает оба пробела: ms-viewer заводит маленький метакэш + push WS клиентам.

Зависимости спеки: 0029, 0030.

## Files

### New files

- `internal/infrastructure/kafka/config_changed_consumer.go` — отдельный consumer-group `ms-viewer-config-changed`, отдельная горутина, не пересекается с `tags.values` consumer.
- `internal/infrastructure/cache/tag_meta_cache.go` — `TagMetaCache`: in-memory `sync.Map`-based; `Get(tagID) (TagMeta, bool)`, `Put(meta)`, `Invalidate(tagID)`, `InvalidateAll()`.
- `internal/usecase/config_change_usecase.go` — `HandleConfigChanged(ev)`: маршрутизация по `entity_type` → инвалидация кэша + push в Hub.
- `internal/realtime/config_broadcast.go` — `Hub.BroadcastConfigChanged(payload)` (отдельный метод, не путать с per-tag publish).

### Modified files

- `internal/usecase/trend_usecase.go` — использовать `TagMetaCache`: cache-aside (`Get` → если miss, читать из БД и `Put`).
- `internal/usecase/diagram_usecase.go` — то же для метаданных тегов в `/api/diagrams/{id}` (figures с привязанными тегами).
- `internal/realtime/protocol.go` — добавить server→client сообщение `{ "t": "config.changed", "entity_type", "entity_id", "operation", "timestamp" }`.
- `internal/realtime/hub.go` — метод `BroadcastConfigChanged` отправляет всем активным соединениям. Без подписок (это глобальный broadcast).
- `internal/config/config.go`:
  - `KafkaConfigChangedTopic` (default `"config.changed"`)
  - `KafkaConfigChangedGroup` (default `"ms-viewer-config-changed"`)
  - `TagMetaCacheSize` (default 10000) — LRU-cap; при превышении — eviction по LRU.
  - `TagMetaCacheTTLSec` (default 600) — soft TTL, чтобы не висели бесконечно при отсутствии invalidate-events.
- `cmd/ms-viewer/main.go` — wire новый consumer и cache.

### Frontend (`viewer-ui/src/`)

- `shared/modules/realtime/types.ts` — TS-зеркало нового `config.changed` сообщения.
- `shared/modules/realtime/store.ts` — добавить slot `lastConfigChange: { entity_type, entity_id, operation, timestamp } | null`.
- `pages/DiagramPage/index.tsx` — на `config.changed` с `entity_type ∈ {diagram, figure}` И `entity_id` совпадает с текущей мнемосхемой (или `figure.diagram_id` совпадает) → показать non-blocking notification «Мнемосхема обновлена» с кнопкой «Обновить» (повторный fetch); авто-перезагрузка через 30s, если оператор не отреагировал.
- `pages/TrendsPage/index.tsx` — на `config.changed` с `entity_type === "tag"` И `entity_id` ∈ `selectedTagIds` → автоматически перезагрузить мета (имя/единица); серии данных не перезагружаем (значения те же).

## Interface

### Backend — `HandleConfigChanged`

```go
func (uc *ConfigChangeUseCase) HandleConfigChanged(ctx context.Context, ev domain.ConfigChangedEvent) error
```

Маршрутизация:

| `entity_type` | Действие |
|---|---|
| `tag`     | `tagMetaCache.Invalidate(entity_id)`. Если `operation == "deleted"` — также `realtime.UnsubscribeTagFromAll(tagID)` (закрыть подписки на удалённый тег). Hub.Broadcast. |
| `device`  | Извлечь `tag_id`-ы из payload (если есть) или `tagMetaCache.InvalidateByDevice(device_id)`; иначе `InvalidateAll()` (cold-start стратегия). Hub.Broadcast. |
| `object`  | `tagMetaCache.InvalidateAll()` (грубо, но события object’ов редкие). Hub.Broadcast. |
| `diagram` | Не трогаем `tagMetaCache`. Только Hub.Broadcast. |
| `figure`  | Не трогаем `tagMetaCache`. Hub.Broadcast (с `entity_type: figure`); фронт сам решит, к какой мнемосхеме относится. Это требует, чтобы payload содержал `diagram_id` — см. § Constraints. |
| иное      | Лог `warn: unknown entity_type`, без действий. |

Любая ошибка handler’а → лог + НЕ коммитим offset (повторим). Идемпотентно: повторное событие приведёт к повторной инвалидации (no-op) и повторному broadcast (frontend увидит «обновлено» дважды — приемлемо).

### Backend — `TagMetaCache`

```go
type TagMeta struct {
    TagID      string
    TagName    string
    DeviceID   string
    DeviceName string
    Unit       UnitInfo
    DataType   DataTypeInfo
    LoadedAt   time.Time
}

type TagMetaCache interface {
    Get(tagID string) (TagMeta, bool)
    Put(meta TagMeta)
    Invalidate(tagID string)
    InvalidateByDevice(deviceID string)
    InvalidateAll()
    Stats() CacheStats // hits, misses, size
}
```

LRU + soft-TTL: запись пропадает либо по invalidate-событию, либо при превышении `TagMetaCacheTTLSec` с момента `LoadedAt`. Реализация — `hashicorp/golang-lru/v2` (`expirable.LRU`).

### Backend — расширение WS-протокола

Server → Client (новое):
```json
{ "t": "config.changed", "entity_type": "diagram", "entity_id": "uuid", "operation": "published", "timestamp": "RFC3339" }
```

Это **глобальное** сообщение — всем подключённым клиентам. Frontend сам фильтрует по `entity_id` относительно текущего экрана.

### Frontend — `ConfigChangeNotification`

Mantine `Notification` (через `@mantine/notifications`):
- При диаграмма-релевантном событии: title «Мнемосхема обновлена», message «Откройте новую версию», action-button «Обновить».
- Цвет — `alarm-warn` (янтарный).
- Auto-close 30s; при автоклоузе — автоматический `refetch` мнемосхемы.
- При тег-релевантном событии: тихая перезагрузка меты, без notification (имена обновятся в легенде графика).

## Constraints

### Backend

- Consumer-group `ms-viewer-config-changed` — отдельная (не разделяем с `tags.values`). Разные consumer-group’ы → разные offset’ы.
- При старте сервиса cache холодный — это нормально. Прогрев не делаем.
- На ошибки парсинга JSON — лог + `commit` (не блокировать поток): такие сообщения непригодны, держать их в backlog бессмысленно.
- `Hub.BroadcastConfigChanged` — без блокировки на каналах: если у соединения outbox переполнен, `config.changed` дропается так же, как и `value` (drop oldest); важнее не повесить весь сервис.
- LRU-кэш не должен утечь: `TagMetaCacheSize=10000` достаточно для сотен мнемосхем; в лог выводить `Stats()` каждые 5 минут (debug).
- Гонка «инвалидация → загрузка»: при cache-aside возможна классическая race (request A прочитал stale, request B успел invalidate, request A запишет stale обратно). Принимаем на себя — следующий запрос корректирует. Альтернатива (single-flight) — overengineering для MVP.
- **Контракт ms-editor (требование)**: при публикации event `figure.created/updated/deleted` payload **обязан** содержать `diagram_id`. Если ms-editor этого не гарантирует — отдельная мини-задача в `ms-editor` (фиксируется как зависимость, в ревью ms-editor’а проверим). До тех пор — fallback: `figure`-event обрабатывается как «relevant ко всем мнемосхемам», шлётся всем (frontend слегка пере-fetch’ит).

### Frontend

- `config.changed` обрабатывается централизованно в `RealtimeClient.on("config.changed", ...)` подписке на уровне `app/App.tsx` или специализированного hook’а. Page-level handlers подписываются через тот же `client.on(...)`.
- Не показывать notification, если страница уже автоматически перезагрузилась (например, после реконнекта `snapshot` уже актуален). Проверка по timestamp последнего fetch’а.
- При множественных `config.changed` за короткий промежуток (>1 в 5s) — coalesce: один notification, один refetch.
- Автоклоуз 30s — НЕ через `setTimeout` в компоненте: использовать `autoClose: 30000` Mantine Notifications API.

## Verify

### Backend

- `go test ./internal/infrastructure/cache/...` — race-free (с `-race`).
- Опубликовать вручную `config.changed { entity_type: "tag", entity_id: <id>, operation: "updated" }` через `kafkacat`:
  - В логе ms-viewer: `cache.invalidate{type=tag,id=...}`.
  - Hub broadcast виден в DevTools WS frames у клиентов.
- Опубликовать `entity_type: "tag", operation: "deleted"`:
  - Те же действия + `unsubscribe_from_all` для этого тега (если кто-то был подписан).
  - В логе соединений видно `unsubscribe{topic=tag:<id>}` от сервера.
- Перерасход событий (1000 за секунду): cache LRU стабилен, RAM не растёт неограниченно.
- Killing kafka во время потока config.changed → consumer останавливается, при возврате — продолжает с offset’а.
- `Stats()` показывает hits/misses; при первом `/api/trends/<id>` — miss, при повторном (в течение TTL) — hit.

### Frontend

- Открыть `/objects/.../diagrams/<id>` → отредактировать схему в ms-editor → опубликовать → у оператора появилось notification «Мнемосхема обновлена», клик «Обновить» → схема перезагружается без F5.
- Не нажимать «Обновить» 30s → автоматический reload, notification закрывается.
- На `/trends` с выбранным тегом: переименовать тег в editor (event `tag.updated`) → имя в легенде обновилось без перезагрузки графика; новые точки не запрашивались.
- `entity_type: "diagram"` при открытом `/trends` — никаких действий (нерелевантно текущему экрану).
- Burst из 5 событий за 2s → один notification, один refetch.
- `RealtimeStatus = closed` (WS оборван) → события не приходят; после реконнекта — `snapshot` обновляет видимое, notification может не показываться (проверка по timestamp).
