# 0017: editor-ui — Страница тегов объекта

## Scope

`editor-ui` — `pages/TagsPage`, `entities/tags`, `widgets/TagDrawer`, `shared/ui/components/`. Вкладка «Теги» внутри `ObjectDetailPage`.

Также: **минимальное расширение backend** `ms-editor` — добавить фильтры `object_id` и `unit_id` в `GET /tags` (см. §10).

## Context

Страница тегов — вкладка в карточке объекта (`/objects/:objectId/tags`). Инженер видит таблицу тегов всех устройств текущего объекта, фильтрует по устройству / типу данных / единице измерения, добавляет новые теги, редактирует адрес/scaling/setpoints и удаляет.

Форма тега зависит от типа устройства (протокола), к которому он привязан:
- **Modbus RTU/TCP** — поля адреса: `register_type` (holding/input/coil/discrete), `address` (0..65535).
- **SNMP v1/v2c/v3** — поля адреса: `oid` (формат `^[0-9]+(\.[0-9]+)+$`).

Кроме адреса, форма содержит общие поля (тип данных, единица), а также два опциональных блока — **scaling** (масштабирование raw → eng) и **setpoints** (LoLo/Lo/Hi/HiHi).

Зависимости:
- **0008** (Objects page) — маршрутизация, ListLayout, ObjectDetailPage, фасадные компоненты, API-клиент.
- **0010** (Devices page) — `entities/devices` (список устройств объекта используется для фильтра и для определения `typeName` тега).
- **0004** (ms-editor tag CRUD) — бэкенд API.
- **0007** (ms-editor validation) — валидация address/setpoints/scaling, RFC 7807.
- `docs/03_Модель-данных/tags/Tags.md`, `Tag_params.md`, `Tag_setpoints.md`, `Tag_Scaling.md`, `Data_types.md`, `Units.md` — модель данных.
- `docs/06_Дизайн/Information-Architecture.md` §7, §8 — IA.

## 1. User Flow

### 1.1 Просмотр таблицы тегов

```
Пользователь на /objects/:objectId → кликает вкладку «Теги»
  → Навигация на /objects/:objectId/tags
  → Контент: заголовок «Теги» + кнопка «Добавить тег» + фильтры + таблица + пагинация

  Таблица:
  ┌────────────────────────────────────────────────────────────────────────────┐
  │ Название       │ Устройство   │ Тип данных │ Единица │ Адрес       │       │
  ├────────────────────────────────────────────────────────────────────────────┤
  │ T_supply       │ PLC-01       │ float32    │ °C      │ holding/100 │ ✏️ 🗑 │
  │ P_main         │ PLC-01       │ float32    │ kPa     │ holding/102 │ ✏️ 🗑 │
  │ Switch.if1.in  │ Switch-Core  │ uint32     │ —       │ 1.3.6.1.2.… │ ✏️ 🗑 │
  └────────────────────────────────────────────────────────────────────────────┘
```

### 1.2 Фильтрация и поиск

```
Над таблицей:
  [🔍 Поиск по имени...] [Устройство: Все ▾] [Тип данных: Все ▾] [Единица: Все ▾]

  → Поиск (search): server-side, передаётся в GET /tags?object_id=…&search=…
  → Фильтр по устройству: Select из устройств этого объекта (через entities/devices store)
  → Фильтр по типу данных: Select из GET /data-types (cached)
  → Фильтр по единице: Select из GET /units (cached, группировка по category)
  → Фильтры комбинируются (AND), все передаются в query params, пагинация сбрасывается на offset=0
```

### 1.3 Добавление тега

```
Пользователь нажимает «Добавить тег»
  → Открывается Drawer справа (width 480px)
  → Шапка: «Новый тег»
  → Форма (шаг 1 — общие поля):
    - Устройство (Select, обязательное) → опции из entities/devices (только устройства этого объекта)
    - Название (TextInput, обязательное)
    - Описание (Textarea, опциональное)
    - Тип данных (Select, обязательное) → опции из GET /data-types
    - Единица (Select, опциональное, clearable) → опции из GET /units, группировка по category

  → После выбора устройства появляется блок «Адрес»:

    Если устройство Modbus (modbus_rtu | modbus_tcp):
      - Тип регистра (Select, обязательное, опции: Holding, Input, Coil, Discrete)
      - Адрес регистра (NumberInput, обязательное, 0..65535)

    Если устройство SNMP (snmp_v1 | snmp_v2c | snmp_v3):
      - OID (TextInput, обязательное, placeholder «1.3.6.1.2.1.1.1.0»)

  → Блок «Масштабирование» (Switch «Использовать»):
      Если включён → 6 опциональных полей (NumberInput): raw_min, raw_max, eng_min, eng_max, factor, offset
      Подсказка под блоком: «Линейная интерполяция: укажите все 4 поля raw/eng. Либо factor/offset.»

  → Блок «Уставки» (Switch «Использовать»):
      Если включён → 4 опциональных поля (NumberInput): LoLo, Lo, Hi, HiHi
      Подсказка: «Должно выполняться LoLo < Lo < Hi < HiHi (для заполненных).»

  → Submit → POST /devices/:deviceId/tags
     body: {
       name, description,
       params: { data_type_id, unit_id, address: { ... } },
       scaling?: { raw_min, raw_max, eng_min, eng_max, factor, offset },
       setpoints?: { lolo, lo, hi, hihi }
     }
  → Drawer закрывается
  → Тег появляется в таблице
  → При ошибке валидации (RFC 7807): подсветка полей по errors[].field
```

### 1.4 Редактирование тега

```
Пользователь нажимает ✏️ в строке таблицы
  → GET /tags/:id → загрузка полных данных (включая params, setpoints, scaling)
  → Открывается Drawer с предзаполненными полями
  → Шапка: «Редактирование: T_supply»
  → Поле «Устройство» — disabled (смена устройства = удаление и создание нового тега)
  → Submit:
      • Имя/описание изменены  → PATCH /tags/:id  body: { name?, description? }
      • Params изменены        → PUT /tags/:id/params  body: { data_type_id, unit_id, address }
      • Setpoints включены/изменены → PUT /tags/:id/setpoints
      • Setpoints выключены    → DELETE /tags/:id/setpoints
      • Scaling включён/изменён → PUT /tags/:id/scaling
      • Scaling выключен       → DELETE /tags/:id/scaling
     Запросы выполняются последовательно; при ошибке любого — Drawer остаётся открыт, ошибка показывается.
  → Drawer закрывается, строка таблицы обновляется
```

### 1.5 Удаление тега

```
Пользователь нажимает 🗑 в строке таблицы
  → Открывается Modal подтверждения:
    «Удалить тег "T_supply"? Это действие нельзя отменить.»
  → Кнопки: «Удалить» (danger) / «Отмена» (secondary)
  → Submit → DELETE /tags/:id
  → Строка исчезает из таблицы
```

### 1.6 Empty state

```
Нет тегов у объекта (но есть устройства)
  → Иконка + текст «У этого объекта нет тегов»
  → Кнопка «Добавить первый тег»

Нет устройств у объекта
  → Иконка + текст «Сначала добавьте устройство во вкладке "Устройства"»
  → Кнопка «Перейти к устройствам» → /objects/:id/devices
```

## 5. API-интеграция

### 5.1 Типы

```ts
// entities/tags/types.ts

export type DeviceProtocol = "modbus_rtu" | "modbus_tcp" | "snmp_v1" | "snmp_v2c" | "snmp_v3";

export type ModbusRegisterType = "holding" | "input" | "coil" | "discrete";

export interface ModbusAddress {
  register_type: ModbusRegisterType;
  address: number; // 0..65535
}

export interface SnmpAddress {
  oid: string; // "^[0-9]+(\.[0-9]+)+$"
}

export type TagAddress = ModbusAddress | SnmpAddress;

export interface TagParams {
  id: string;
  data_type_id: number;
  unit_id: number | null;
  address: TagAddress;
  created_at: string;
  updated_at: string;
}

export interface TagSetpoints {
  lolo: number | null;
  lo: number | null;
  hi: number | null;
  hihi: number | null;
}

export interface TagScaling {
  raw_min: number | null;
  raw_max: number | null;
  eng_min: number | null;
  eng_max: number | null;
  factor: number | null;
  offset: number | null;
}

export interface Tag {
  id: string;
  device_id: string;
  name: string;
  description: string | null;
  params: TagParams | null;
```

### 5.2 API-функции

```ts
// entities/tags/api.ts

import { api } from "@shared/api";
import type { PaginatedResponse } from "@shared/api";
import type {
  Tag, CreateTagPayload, UpdateTagPayload, UpdateTagParamsPayload,
  TagSetpoints, TagScaling, TagsListFilters,
} from "./types";

export const tagsApi = {
  list: (filters: TagsListFilters) =>
    api.get<PaginatedResponse<Tag>>("/tags", filters),

  get: (id: string) =>
    api.get<Tag>(`/tags/${id}`),

  create: (deviceId: string, payload: CreateTagPayload) =>
    api.post<Tag>(`/devices/${deviceId}/tags`, payload),

  update: (id: string, payload: UpdateTagPayload) =>
    api.patch<Tag>(`/tags/${id}`, payload),

  updateParams: (id: string, payload: UpdateTagParamsPayload) =>
    api.put<Tag>(`/tags/${id}/params`, payload),

  putSetpoints: (id: string, payload: TagSetpoints) =>
    api.put<Tag>(`/tags/${id}/setpoints`, payload),

  deleteSetpoints: (id: string) =>
    api.delete(`/tags/${id}/setpoints`),

  putScaling: (id: string, payload: TagScaling) =>
    api.put<Tag>(`/tags/${id}/scaling`, payload),

  deleteScaling: (id: string) =>
    api.delete(`/tags/${id}/scaling`),

  delete: (id: string) =>
    api.delete(`/tags/${id}`),
};
```

## 6. Компоненты

### 6.1 TagsPage

```tsx
export default function TagsPage() {
  const { objectId } = useParams<{ objectId: string }>();
  const { tags, total, isLoading, filters, setFilters, fetchTags, reset } = useTagsStore();
  const { devices, fetchDevices } = useDevicesStore();
  const { items: dataTypes, fetch: fetchDataTypes } = useDataTypesStore();
  const { items: units, fetch: fetchUnits } = useUnitsStore();

  useEffect(() => {
    setFilters({ object_id: objectId, offset: 0 });
    fetchDevices(objectId!);
    fetchDataTypes();
    fetchUnits();
    fetchTags();
    return () => reset();
  }, [objectId]);

  useEffect(() => { fetchTags(); }, [filters]);

  const [drawerMode, setDrawerMode] = useState<"closed" | "create" | "edit">("closed");
  const [editTagId, setEditTagId] = useState<string | null>(null);

  return (
    <>
      <Group justify="space-between" mb="md">
        <Text size="xl" fw={600}>Теги</Text>
        <Button variant="primary" disabled={devices.length === 0} onClick={() => setDrawerMode("create")}>
          Добавить тег
        </Button>
      </Group>

      <Group mb="md" gap="sm">
        <TextInput placeholder="Поиск по имени..." value={filters.search ?? ""} onChange={...} />
        <Select placeholder="Устройство" data={devices.map(...)} value={filters.device_id ?? null} onChange={...} clearable />
        <Select placeholder="Тип данных" data={dataTypes.map(...)} value={...} onChange={...} clearable />
        <Select placeholder="Единица" data={groupUnits(units)} value={...} onChange={...} clearable searchable />
      </Group>

      {isLoading
        ? <SkeletonTable />
        : devices.length === 0
          ? <NoDevicesEmptyState objectId={objectId!} />
          : tags.length === 0
            ? <EmptyState onAdd={() => setDrawerMode("create")} />
            : <TagsTable tags={tags} devices={devices} dataTypes={dataTypes} units={units}
                         onEdit={(id) => { setEditTagId(id); setDrawerMode("edit"); }}
                         onDelete={(id) => { /* confirm modal → deleteTag */ }} />}

      <Pagination total={Math.ceil(total / (filters.limit ?? 50))} value={...} onChange={...} />

      <TagDrawer
        opened={drawerMode !== "closed"}
        mode={drawerMode === "edit" ? "edit" : "create"}
        tagId={editTagId}
        objectId={objectId!}
        onClose={() => { setDrawerMode("closed"); setEditTagId(null); }}
      />
    </>
```

### 6.4 Сохранение правок (edit mode)

`saveTagEdits(id, diff)` в store вычисляет, какие части тега изменились, и выполняет минимальный набор запросов:

```ts
type TagEditDiff = {
  meta?: UpdateTagPayload;                 // PATCH /tags/:id
  params?: UpdateTagParamsPayload;         // PUT  /tags/:id/params
  setpoints?: TagSetpoints | "delete";     // PUT  или DELETE /tags/:id/setpoints
  scaling?:   TagScaling   | "delete";     // PUT  или DELETE /tags/:id/scaling
};
```

Диф вычисляется в `TagDrawer` сравнением начального и текущего состояния. Запросы выполняются последовательно (await за await) — при ошибке любого Drawer остаётся открыт.

### 6.5 TagAddressForm — динамические поля

```tsx
interface TagAddressFormProps {
  protocol: DeviceProtocol | null;
  address: Partial<TagAddress>;
  onChange: (address: TagAddress) => void;
  errors?: Record<string, string>;
}

export const TagAddressForm = ({ protocol, address, onChange, errors }: TagAddressFormProps) => {
  if (!protocol) return null;
  if (protocol === "modbus_rtu" || protocol === "modbus_tcp") {
    return <ModbusAddressFields address={address} onChange={onChange} errors={errors} />;
  }
  return <SnmpAddressFields address={address} onChange={onChange} errors={errors} />;
};
```

`protocol` определяется по выбранному устройству:
```ts
const selectedDevice = devices.find(d => d.id === formState.device_id);
const protocol = selectedDevice?.typeName ?? null;
```

### 6.6 Валидация

**Клиентская (базовая):**
- `name` — не пустое.
- `device_id`, `data_type_id` — выбраны.
- Address для Modbus: `register_type` выбран, `address` ∈ [0, 65535].
- Address для SNMP: `oid` соответствует regexp `^[0-9]+(\.[0-9]+)+$`.
- Setpoints (если включены): для заполненных пар проверка LoLo<Lo<Hi<HiHi.
- Scaling (если включён): либо все 4 raw/eng заполнены, либо ни одного; `raw_min !== raw_max`; `factor !== 0`.

**Серверная (RFC 7807):**
- Маппинг `errors[].field` на поля формы:
  - `name`, `description`, `params.data_type_id`, `params.unit_id` → одноимённые поля.
  - `address.register_type`, `address.address`, `address.oid` → поля адреса.
  - `lolo`, `lo`, `hi`, `hihi` → поля setpoints.
  - `raw_min`, `raw_max`, `eng_min`, `eng_max`, `factor`, `offset` → поля scaling.

## 9. Constraints

- **Фасадный паттерн**: Switch и любые новые Mantine-компоненты — только через `shared/ui/components/`. Не импортировать `@mantine/core` напрямую вне фасадов.
- **FSD**: TagDrawer — widget. *Fields-компоненты — внутренние модули TagDrawer (не экспортируются наружу). TagsTable — widget.
- **Устройство нередактируемое**: при edit mode Select устройства disabled. Смена устройства = удаление и создание нового тега.
- **Cached справочники**: `data-types` и `units` загружаются один раз и живут в своих store; повторные запросы переиспользуют кеш.
- **Минимальный набор запросов в edit mode**: вычислять диф и слать только изменённые блоки (см. §6.4). Не делать «PUT всё всегда».
- **Адрес как JSONB**: на клиенте — типизированный union `ModbusAddress | SnmpAddress`. На отправку — сериализуется как есть, бэкенд валидирует структуру.
- **Server-side фильтры/пагинация**: фильтры передаются в `GET /tags`, пагинация серверная (`offset`/`limit`/`total` из ответа).
- **Не реализовывать**: bulk-операции (массовое удаление/импорт), copy-tag, привязку тегов к фигурам мнемосхемы (это в 0011).

## 10. Backend prerequisites (требуется для этого UI)

`GET /tags` сегодня поддерживает фильтры `device_id`, `data_type_id`, `search`. Для страницы тегов объекта необходимо добавить:

| Фильтр | Где | Реализация |
|--------|-----|-----------|
| `object_id` | `parseTagListQuery` + `domain.TagListQuery.ObjectID` + `ListTags` SQL | `LEFT JOIN devices.devices d ON d.id = t.device_id`, `WHERE d.object_id = $X AND d.deleted_at IS NULL` |
| `unit_id` | `parseTagListQuery` + `domain.TagListQuery.UnitID` + `ListTags` SQL | `LEFT JOIN tags.tag_params tp ON tp.tag_id = t.id`, `WHERE tp.unit_id = $X` (JOIN уже есть, см. spec 0005) |

Эти расширения должны попасть **в эту же спеку** при реализации (или быть выделены в отдельную микро-спеку перед ней). Без них фронт не сможет:
- показать «теги объекта» (нужен `object_id`),
- фильтровать таблицу по единице (нужен `unit_id`).

Контракт `GET /tags` после расширения:

```
GET /tags?object_id={uuid}&device_id={uuid}&data_type_id={int}&unit_id={int}&search={str}&offset={int}&limit={int}
```

Все фильтры опциональны и комбинируются через AND.
