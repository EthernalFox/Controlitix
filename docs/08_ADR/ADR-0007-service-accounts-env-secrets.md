# ADR-0007: ТУЗ и секреты в env для межсервисной аутентификации

- Статус: accepted
- Дата: 2026-04-15
- Авторы: команда Controlitix

## Контекст

Сервисы Controlitix обмениваются запросами напрямую (в основном через Kafka и REST). Нужно ответить на два вопроса:

1. Как сервисы аутентифицируются друг перед другом (например, когда `ms-viewer` зовёт `ms-editor` за метаданными, или когда `ms-poll` читает конфигурацию).
2. Где хранятся секреты (ключи ТУЗ, пароли к БД, токен Telegram-бота, SNMP community strings, параметры Modbus-соединений).

## Рассмотренные варианты

### Межсервисная аутентификация

1. **Без аутентификации внутри сети Compose** — полагаемся на изоляцию Docker network.
2. **ТУЗ (технологическая учётная запись) с секретом** — каждый сервис имеет собственный service account в `ms-auth`, получает service-JWT и предъявляет его при межсервисных запросах.
3. **mTLS между всеми сервисами** — строго и надёжно, но требует PKI и усложняет Compose-разворот.

### Хранение секретов

1. **Переменные окружения (`.env`)** — стандарт Compose, просто, без дополнительных зависимостей.
2. **HashiCorp Vault / SOPS / Sealed Secrets** — централизованное управление секретами, ротация, аудит. Избыточно для одного хоста.
3. **Docker secrets** — работает только в Swarm-режиме, не в обычном Compose.

## Решение

### Межсервисная аутентификация — ТУЗ

Каждый сервис (`ms-editor`, `ms-poll`, `ms-viewer`) имеет свою **технологическую учётную запись** в `ms-auth` с фиксированным **client_id** и **client_secret**:

- `client_id` + `client_secret` передаются сервису через env.
- При старте сервис запрашивает у `ms-auth` короткоживущий **service-JWT** (client_credentials grant).
- Service-JWT содержит `sub=svc:ms-poll` и список разрешённых scope (например, `config.read`, `tags.values.write`).
- Service-JWT передаётся в заголовке `Authorization: Bearer <token>` при межсервисных вызовах и валидируется приёмником локально через публичный ключ `ms-auth` (JWKS).
- TTL service-JWT — 15 минут, сервис обновляет заранее.

Это же решение используется для **пользовательских** токенов (user-JWT), выдаваемых `ms-auth` при логине. Приёмник не различает источник токена — важен только scope и audience.

### Секреты — env

Секреты хранятся в **`.env`-файлах Docker Compose**:

- `.env` — пример/шаблон в репозитории (без настоящих значений).
- `.env.local` / `.env.production` — реальные значения, **не коммитятся**, живут на хосте.
- Права на файл — `0600`, владелец — пользователь, под которым запускается Compose.
- Набор секретов: `POSTGRES_PASSWORD`, `MS_*_CLIENT_SECRET`, `MS_AUTH_JWT_PRIVATE_KEY`, `TELEGRAM_BOT_TOKEN`, `NGINX_TLS_CERT_PATH`/`NGINX_TLS_KEY_PATH`.

**Ротация секретов** — ручная: заменить значение в `.env`, пересоздать контейнер. Автоматическая ротация — вне MVP.

## Последствия

**Позитивно:**

- Минимум инструментов, команда контролирует всё из одного репозитория и одного `.env`.
- Единый механизм токенов (user + service), одинаково валидируется во всех сервисах через JWKS.
- Простая модель scope и audience работает уже сейчас и готова к расширению (добавление прав без перестройки архитектуры).

**Негативно:**

- Секреты в plain-text на диске хоста. Защита — только права доступа ОС и физическая безопасность.
- Ротация секретов требует перезапуска контейнеров.
- Нет централизованного аудита доступа к секретам.
- При переезде в SaaS/облако потребуется переехать на Vault или managed secret store (ADR-будущее).

**Исключено из MVP:**

- Vault / KMS / Secret Manager.
- Автоматическая ротация.
- mTLS между сервисами.
