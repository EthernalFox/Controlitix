# 0015: ms-poll — драйверы Modbus TCP и Modbus RTU

## Scope

`ms-poll`. Этот спек добавляет конкретные реализации `domain.Driver` для Modbus TCP и Modbus RTU поверх библиотеки `github.com/goburrow/modbus`. Также вводится сериализация доступа к serial-портам (один RTU-порт может обслуживать несколько устройств с разными `unit_id`).
Никакой нормализации значений и никакой публикации в Kafka — только сырые чтения и формирование `Reading`. Нормализация и Kafka — спек 0016.

## Context

- Базовый фреймворк драйверов: спек [`0014.ready.ms-poll-scheduler-driver-framework.md`](0014.ready.ms-poll-scheduler-driver-framework.md).
- Roadmap Phase 4.2 (Modbus TCP) и 4.3 (Modbus RTU).
- Источник правды для адресов:
  - `devices.devices_params.settings` (JSONB).
  - `tags.tag_params.address` (JSONB).
- Формат `device.settings`:
  - `modbus_tcp`: `{"host":"192.168.1.10","port":502,"unit_id":1,"timeout_ms":1000}`.
  - `modbus_rtu`: `{"port":"/dev/ttyUSB0","baud_rate":9600,"data_bits":8,"parity":"N","stop_bits":1,"unit_id":1,"timeout_ms":1000}`.
- Формат `tag.address`: `{"register_type":"holding|input|coil|discrete","address":40001,"length":1}`.
  - `address` — Modbus-адрес в нумерации 4xxxx/3xxxx/0xxxx/1xxxx (как в инженерных тулзах). Для `holding` валидный диапазон `40001-49999`, для `input` — `30001-39999`, для `coil` — `00001-09999`, для `discrete` — `10001-19999`. Внутри драйвера приводим к 0-based offset (`address - 40001`).
  - `length` — опционально, по умолчанию `1`. Используется только для `holding`/`input` (для float32 нужно 2 регистра, для int64 — 4).
- `data_type` тега из `tags.data_types.name`. Драйвер использует его, чтобы понять, сколько регистров читать и как декодировать байты:
  - `bool` → 1 coil/discrete или младший бит holding.
  - `int8`, `uint8` → 1 регистр (байт в LSB).
  - `int16`, `uint16` → 1 регистр.
  - `int32`, `uint32`, `float32` → 2 регистра (big-endian word order по умолчанию).
  - `float64` → 4 регистра.
  - `string` → `length` регистров, ASCII, trim NUL.

## Files

## Interface

### Address

```go
package modbus

type RegisterType string
const (
    RegHolding  RegisterType = "holding"
    RegInput    RegisterType = "input"
    RegCoil     RegisterType = "coil"
    RegDiscrete RegisterType = "discrete"
)

type ParsedAddress struct {
    RegisterType RegisterType
    Offset       uint16   // 0-based offset для библиотеки goburrow/modbus
    Length       uint16   // в "единицах" (регистрах для holding/input, битах для coil/discrete)
}

func ParseTagAddress(raw json.RawMessage, dataType string) (ParsedAddress, error)
```

`Length` рассчитывается так:

| data_type           | holding/input | coil/discrete | примечание                  |
|---------------------|---------------|---------------|------------------------------|
| `bool`              | 1             | 1             | bool поверх holding — bit0   |
| `int8`/`uint8`      | 1             | n/a           |                              |
| `int16`/`uint16`    | 1             | n/a           |                              |
| `int32`/`uint32`    | 2             | n/a           |                              |
| `float32`           | 2             | n/a           |                              |
| `float64`           | 4             | n/a           |                              |
| `string`            | length из JSON| n/a           | `length` обязателен в JSON   |

Если `register_type=coil|discrete` и `data_type ≠ bool` → ошибка.

### Batch

```go
package modbus

type ReadRequest struct {
    RegisterType RegisterType
    StartOffset  uint16
    Quantity     uint16
    Tags         []*tagSlot       // сопоставление: какие теги покрываются этим запросом и где в буфере их данные
}

type tagSlot struct {
    Tag       *domain.TagSnapshot
    Offset    uint16  // относительно StartOffset, в "единицах"
    Length    uint16  // в "единицах"
}

func BuildBatches(tags []*domain.TagSnapshot) ([]ReadRequest, error)
```

Логика:
- Группируем теги по `RegisterType`.
- Сортируем по `Offset`.
- Склеиваем соседние/перекрывающиеся диапазоны, пока суммарный `Quantity ≤ 125` (для регистров) / `≤ 2000` (для битов).
- Если в одной группе есть тег с невалидным address — возвращаем ошибку из `BuildBatches`. Scheduler залогирует и пропустит этот device.

### TCP Driver

```go
package modbus

type TCPDriverFactory struct{}

func NewTCPDriverFactory() *TCPDriverFactory
func (f *TCPDriverFactory) SupportedType() string { return "modbus_tcp" }
func (f *TCPDriverFactory) Build(device *domain.DeviceSnapshot) (domain.Driver, error)
```

`Build` парсит `device.Settings` в:

```go
type tcpSettings struct {
    Host      string `json:"host"`
    Port      int    `json:"port"`        // default 502
    UnitID    byte   `json:"unit_id"`     // default 1
    TimeoutMs int    `json:"timeout_ms"`  // default 1000
}
```

Создаёт `modbus.NewTCPClientHandler(host:port)`, выставляет `Timeout`, `SlaveId`, `Connect()`. Возвращает `*tcpDriver`, у которого внутри `client modbus.Client` и `handler *modbus.TCPClientHandler`.

`Read`:
1. `BuildBatches(tags)`. При ошибке — все теги получают `Reading{Quality: bad, Error: "..."}`.
2. По каждому `ReadRequest` вызвать соответствующий метод client (`ReadHoldingRegisters` и т.д.).
3. На каждый tag в request:
   - При успехе батча: `DecodeRegisters` или `DecodeBits` → `Reading{Value: ..., Quality: good, ReadAt: time.Now().UTC()}`.
   - При ошибке батча: `Reading{Quality: bad, Error: err.Error(), ReadAt: time.Now().UTC()}` для каждого тега из request.
4. Вернуть слайс длиной `len(tags)` в исходном порядке.

`HealthCheck`: попытаться `ReadHoldingRegisters(0, 1)` (или, если не работает, `ReadCoils(0, 1)`). Любой успешный ответ → `nil`. Ошибка таймаута/сети → возврат error.

`Close`: `handler.Close()`.

### RTU Driver

```go
package modbus

type RTUDriverFactory struct {
    pool *SerialPortPool
}

func NewRTUDriverFactory(pool *SerialPortPool) *RTUDriverFactory
func (f *RTUDriverFactory) SupportedType() string { return "modbus_rtu" }
func (f *RTUDriverFactory) Build(device *domain.DeviceSnapshot) (domain.Driver, error)
```

`rtuSettings`:

```go
type rtuSettings struct {
    Port      string `json:"port"`         // /dev/ttyUSB0 или COM3
    BaudRate  int    `json:"baud_rate"`    // default 9600
    DataBits  int    `json:"data_bits"`    // default 8
    Parity    string `json:"parity"`       // "N"|"E"|"O", default "N"
    StopBits  int    `json:"stop_bits"`    // default 1
    UnitID    byte   `json:"unit_id"`      // default 1
    TimeoutMs int    `json:"timeout_ms"`   // default 1000
}
```

Драйвер при `Build` НЕ открывает порт — он берёт `lock` из pool по ключу `Port` лениво при `Read`/`HealthCheck`, открывает handler, читает, закрывает или держит handler внутри pool (см. ниже). На MVP — открываем при первом `Read` и держим до `Close`.

### SerialPortPool

```go
package modbus

type SerialPortPool struct {
    locks map[string]*sync.Mutex
    mu    sync.Mutex
}

func NewSerialPortPool() *SerialPortPool

// Acquire возвращает мьютекс конкретного порта. Драйвер обязан удерживать его на время одной транзакции (Read/HealthCheck).
func (p *SerialPortPool) Acquire(port string) *sync.Mutex
```

Логика `rtuDriver.Read`:
1. `lock := pool.Acquire(settings.Port); lock.Lock(); defer lock.Unlock()` — ровно одна транзакция на порт в момент времени.
2. Если handler ещё не открыт — открыть `modbus.NewRTUClientHandler(port)` с параметрами, `Connect()`. Сохранить.
3. Перед чтением выставить `handler.SlaveId = settings.UnitID` (важно: разные устройства на одном порту имеют разный unit_id).
4. Дальше — как в TCP драйвере (BuildBatches → ReadX → DecodeY → []Reading).

`Close` закрывает handler.

## Constraints

- Никакой работы с Kafka и нормализации значений в этом спеке — только сырые `Reading` (Value содержит результат `DecodeRegisters`, без factor/offset/scaling).
- Драйвер НЕ возвращает `error` из `Read` (контракт из 0014).
- `BuildBatches` НЕ удаляет «битые» теги — он возвращает все или ошибку. Если один тег с невалидным address — все теги устройства получают bad quality в этом цикле. Это сознательно: проще трассировать.
- Один процесс ms-poll НЕ открывает один и тот же serial-порт дважды. SerialPortPool гарантирует сериализацию, но физическое открытие порта живёт внутри драйвера. Не делать общего connection pool на handler — это усложнит RTU-логику и не нужно при <10 устройств на порт.
- TCP драйвер НЕ переиспользует TCP-соединение между устройствами — каждый `tcpDriver` имеет свой handler. Это нормально для MVP (десятки устройств максимум).
- Зависимость `goburrow/modbus` — единственная новая зависимость в этом спеке. Не тащить дополнительные библиотеки serial.
- Byte/word order захардкодить как ABCD (big-endian, big word). Конфигурация порядка байтов — отдельная задача.
- При парсинге `device.Settings` ВСЕ поля имеют дефолты (см. таблицу). Если `host` или `port` для `modbus_rtu` пустые — ошибка `Build`.
- Не вводить retry на уровне драйвера — retry/backoff живёт в scheduler (фактически в HealthCheck-skip механизме). Один `Read` = одна попытка.

## Verify

- `cd ms-poll && go mod tidy && go build ./... && go vet ./...` зелёное.
- Юнит-тесты `modbus_test.go` (без сети):
  - `ParseTagAddress` для всех `data_type` × `register_type` (валидные и невалидные комбинации).
  - `DecodeRegisters`:
    - holding [0x41, 0x48] → uint16=16712.
    - holding [0x40, 0x49, 0x0F, 0xDB] (float32 ABCD) → ≈3.14159 ±1e-5.
    - holding [0x40, 0x09, 0x21, 0xFB, 0x54, 0x44, 0x2D, 0x18] (float64) → ≈3.14159265358979 ±1e-12.
    - int16 [0xFF, 0xFF] → -1.
  - `DecodeBits([0b00001010], bitIndex=1)` → true; `bitIndex=0` → false.
  - `BuildBatches`:
    - 3 holding-тега подряд (40001, 40002, 40003) → один ReadRequest, Quantity=3.
    - holding на 40001 и 40100 → два ReadRequest (склейка не выгодна — 100 регистров против 99 пустых).
    - 130 holding-тегов подряд → два ReadRequest по ≤125 регистров.
    - holding-тег + coil-тег → два ReadRequest разных типов.
    - Невалидный address → error.
- E2E (ручная проверка с реальным или эмулированным устройством):
  - Поднять Modbus TCP slave (например, `pymodbus`-эмулятор) на `127.0.0.1:1502` с парой holding-регистров.
  - В ms-editor создать устройство `modbus_tcp` с `settings={"host":"127.0.0.1","port":1502,"unit_id":1}` и пару тегов.
  - В логе ms-poll увидеть: `device started type=modbus_tcp`, и каждую секунду `device read device_id=... readings=2 good=2 bad=0`.
  - Остановить эмулятор → следующие читания идут с `quality=bad`, через 10 сек health-check фейлится, `device unhealthy device_id=...`.
  - Поднять снова → `device healthy device_id=...`, чтения возобновляются.
- Modbus RTU smoke-тест (если есть оборудование):
  - Два устройства на одном `/dev/ttyUSB0` с разными `unit_id` → оба обслуживаются последовательно, нет ошибок «port busy».
