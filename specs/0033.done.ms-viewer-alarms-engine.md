# 0033: ms-viewer — Alarms engine (evaluation, persistence, REST, WS, Kafka)

## Scope

Полный alarms-flow в `ms-viewer`:

1. Миграции схемы `alarms`: `alarms.events`, `alarms.states`, `alarms.acks`.
2. Engine: оценка входящих `tags.values` против `tags.tag_setpoints`, гистерезис, suppress, переходы состояний, persistence.
3. REST: `GET /api/alarms`, `GET /api/alarms/{id}`, `POST /api/alarms/{id}/acknowledge`.
4. WS-топик `alarms` (глобальный) — снапшот активных + live-события.
5. Kafka producer `alarms.events` (выходной топик для аудита и downstream-консьюмеров типа notifier).

Out of scope: Telegram-уведомления (это 0035), эскалации (sub-задача 0035), RBAC-проверки на ack (это 0036, в этой спеке `RequireAuth` достаточно).

Зависимости спеки: 0029, 0030, 0032.

```go
    AlarmEventRaised      AlarmEventType = 0
    AlarmEventCleared     AlarmEventType = 1

    AlarmEventUnsuppressed AlarmEventType = 4

```

API отдаёт строкой (`"ok"|"lo"|"hi"|"lolo"|"hihi"|"uncertain"|"bad"|"comm_loss"|"offline"`); БД хранит `smallint`.

### Evaluation logic

```go
type Setpoints struct { LoLo, Lo, Hi, HiHi *float64 }

func Evaluate(
    prev AlarmState,
    value *float64,
    quality Quality,         // из ingest
    setpoints Setpoints,
    hysteresisPercent float64,
) (next AlarmState, changed bool)
```

Правила:

1. Если `quality ∈ {comm_loss, offline}` → `next = AlarmStateCommLoss/Offline`.
2. Если `quality ∈ {bad, uncertain}` или `value == nil` → `next = AlarmStateBad/Uncertain`.
3. Если `quality == ok` (или `hi/hihi/acknowledged` от ms-poll-уровня — игнорируем, оцениваем заново):
   - Сравнить `value` с setpoints в порядке: HiHi > Hi > Lo > LoLo.
   - Если `value >= HiHi` → `Hihi`.
   - Иначе если `value >= Hi` → `Hi`.
   - Иначе если `value <= LoLo` → `LoLo`.
   - Иначе если `value <= Lo` → `Lo`.
   - Иначе → `OK`.
4. **Гистерезис** при возврате (state ↘ к OK): не возвращаемся, пока value не отойдёт от порога на `hysteresisPercent` от диапазона `(HiHi-LoLo)` (или фиксированных 2% от `Hi-Lo`, если нет HiHi/LoLo). Подъём вверх — без гистерезиса (срабатываем сразу).
5. Если setpoints пустые (нет ни одного порога) — состояние всегда `OK` (если quality OK) или `Bad/CommLoss` (иначе).

`changed` — true если `prev != next`. Только при `changed == true` запускается transition-pipeline (persist event, Kafka, WS).

### Persistence pipeline (на каждый ingest)

```
IngestUseCase.IngestTagValue(record)
   ↓ (in-memory)
   AlarmUseCase.Evaluate(record)
   ↓ if transition:
   tx := db.Begin()
   tx.Upsert(alarms.states {tag_id, state=next, last_value, ...})
   tx.Insert(alarms.events {tag_id, event_type=raised|cleared, state_from=prev, state_to=next, ...})
   tx.Commit()
   ↓
   alarmsKafkaProducer.Publish(event)   // best-effort, retry
   ↓
   hub.BroadcastAlarm(event)            // всем подписчикам топика "alarms"
```

Setpoints читаются один раз на старте сервиса (in-memory `map[tag_id]Setpoints`); инвалидация — на `config.changed { entity_type: "tag", operation: "updated|deleted" }` (см. 0032).

`alarms.acks` сбрасывается автоматически при `cleared` (transition в OK) — `DELETE FROM alarms.acks WHERE tag_id = $1`.

### Comm-loss detection (timer-based)

Отдельная горутина каждые 30s сканирует `alarms.states WHERE last_seen_at < now() - INTERVAL 'N seconds' AND state != comm_loss/offline` (где N = `AlarmCommLossTimeoutSec`). Найденные → transition в `CommLoss`, persistence, Kafka, WS.

### REST endpoints

#### `GET /api/alarms`

Query:
- `status` — `active | acked | cleared` (default `active`).
- `severity` — `info | warn | alarm` (где `info=lo+hi`, `warn=lo+hi`, `alarm=lolo+hihi`; alias’ы — см. § Constraints).
- `object_id` — фильтр (резолвится через `tag_id → device → object_id`).
- `from`, `to` — для `cleared`-вкладки.
- `limit` (default 50, max 500), `offset`.

Ответ:
```json
{
  "items": [
    {
      "tag_id": "uuid",
      "tag_name": "boiler_1.t_out",
      "device_id": "uuid", "device_name": "Boiler-1",
      "object_id": "uuid", "object_name": "Котельная №3",
      "state": "hihi",
      "value": 95.4, "quality": "hihi",
      "entered_at": "2026-04-25T10:01:00Z",
      "last_seen_at": "2026-04-25T10:05:30Z",
      "acked": false,
      "ack": null
    }
  ],
  "total": 17, "offset": 0, "limit": 50
}
```

`active` — `state > 0 AND tag_id NOT IN (SELECT tag_id FROM alarms.acks)`.

#### `GET /api/alarms/{tagId}`

Текущее состояние + последние 50 событий по тегу.

#### `POST /api/alarms/{tagId}/acknowledge`

Body: `{ "note": "string|null" }`.

Логика:
1. SELECT `alarms.states WHERE tag_id = $1`. Нет → 404.
2. Если `state == 0` → 409 `/errors/alarms/not-active` (нечего квитировать).
3. INSERT/UPDATE `alarms.acks { tag_id, state, actor_id = principal.subject, note, acked_at = now() }`.
4. INSERT `alarms.events { event_type = acked, ... }`.
5. Kafka publish + Hub.BroadcastAlarm.

Ответ 200 `{ tag_id, state, acked: true, ack: { actor_id, acked_at, note } }`.

#### Errors

| Type | Status |
|---|---|
| `/errors/alarms/not-found` | 404 |
| `/errors/alarms/not-active` | 409 |
| `/errors/alarms/already-acked` | 409 |

### WS-топик `alarms`

Subscribe: `{ "t": "subscribe", "topics": ["alarms"] }` → ответ `subscribed` + сразу snapshot всех активных тревог:

```json
{ "t": "alarms_snapshot", "ts": "...", "items": [ { ...AlarmRecord }, ... ] }
```

Live-события на тот же канал:
```json
{ "t": "alarm", "event_type": "raised|cleared|acked", "tag_id": "...", "state_from": "ok", "state_to": "hi", "value": 75.4, "quality": "hi", "ts": "...", "actor_id": null, "note": null }
```

`AlarmRecord` для snapshot — тот же DTO, что в `/api/alarms`.

### Kafka topic `alarms.events`

Producer пишет JSON, key = `tag_id`. Формат — тот же DTO, что в WS `alarm`-сообщении (без обёртки `t`).

Это выходной поток для downstream-сервисов (notifier — 0035, audit — 0036, аналитика).

## Constraints

### Backend

- Engine — синхронный относительно ingest-pipeline: transition должна быть устойчиво записана в БД до Kafka publish (избегаем «опубликовали, но не сохранили»). Порядок: tx.Commit() → Kafka.Publish() → Hub.Broadcast. Kafka publish при отказе ретраится фоном (не блокирует ingest); WS broadcast — fire-and-forget.
- Идемпотентность: повторный ingest того же `(tag_id, ts)` не должен создавать дубликат события. Защита — проверка `prev != next` ДО tx; если `prev == next` — exit-no-op. (Истинный дубликат значения редкий, но при перезапуске kafka consumer он реально случается.)
- Setpoints in-memory map на старте: запрос `SELECT tp.tag_id, sp.lolo, sp.lo, sp.hi, sp.hihi FROM tags.tag_params tp LEFT JOIN tags.tag_setpoints sp ON sp.param_id = tp.id WHERE tp.deleted_at IS NULL`. На `config.changed` — точечно reload по `tag_id`.
- Отсутствие setpoints у тега ≠ ошибка. Тег без порогов — никогда не уходит в alarm (только в comm_loss/bad по quality).
- Гистерезис применяется только в направлении OK; апвард-переходы мгновенные. Это конвенция SCADA (быстро поймать аварию, медленно квитировать «всё ок»).
- Comm-loss-сканер не должен дёргать БД на каждом тике без индекса. Индекс `states_state_idx WHERE state > 0` уже создан; добавить partial index на `last_seen_at` если профилирование покажет необходимость.
- Severity-маппинг (`info|warn|alarm`) — только в API, в БД хранится state числом; не плодить лишние enum’ы.
- БД-роль: `INSERT/SELECT/UPDATE/DELETE` на `alarms.*`, `SELECT` на `tags.tag_params`, `tags.tag_setpoints` (последнее уже было в 0029 для метаданных).
- Kafka topic `alarms.events` создаётся вручную (или через init-job) с partition = 6, retention = 30d. В этой спеке только producer; топик-конфиг — отдельная задача DevOps.

### Frontend

- `AlarmsPage`: серверная пагинация, не клиентская. Кнопка «Обновить» — рефетч; live-события из WS добавляют наверх таблицы при `status=active`.
- Optimistic ack: при клике сразу метим строку как `acked: true` локально, отправляем POST; при ошибке — откатываем + Notification.
- `AlarmTicker` в `AppHeader` — макс 5 строк; click — переход на `/alarms`.
- Цвет severity (через тех же tokens из Design-System.md):
  - `lolo|hihi` → `alarm-alarm` (красный).
  - `lo|hi` → `alarm-warn` (янтарный).
  - `uncertain` → `alarm-uncertain` (синий).
  - `bad` → `alarm-bad` (серо-голубой).
  - `comm_loss` → `alarm-comm` (тёмно-серый).
  - `offline` → `alarm-offline`.
- Мигание — только для unacknowledged `hi/hihi`. Любые другие — без мигания. Та же логика, что в `0031` `dynamics.blinkOnAlarm`.
- Никаких прямых `@mantine/core` импортов в `pages/AlarmsPage`.
