# 0034: ms-viewer — WS subscriptions для `object:<uuid>` и `diagram:<uuid>`

## Scope

Расширение WS-протокола из 0030: помимо `tag:<uuid>` сервер принимает подписки на `object:<uuid>` и `diagram:<uuid>`. Backend разворачивает их в множества `tag_id` и удерживает соответствие, реагируя на `config.changed` (через 0032).

Out of scope: топик `alarms` (уже в 0033); топик `figures` (нет такой необходимости — фигуры приходят разово в `GET /api/diagrams/{id}`).

Зависимости: 0030, 0032, 0031.

## Context

Виды подписки — требование архитектуры [docs/02_Архитектура/Микросервисы/ms-viewer.md](../docs/02_Архитектура/Микросервисы/ms-viewer.md) § 1: «WebSocket-подписки **по объектам, схемам и тегам**».

Сейчас в 0030 реализован только `tag:<uuid>`. На стороне `viewer-ui` это работает, но неудобно:
- В `pages/DiagramPage` (0031) фронт сам вытаскивает все `tag_id` из figures и подписывается на каждый. Это N подписок в WS-команде вместо одной.
- В будущем DashboardPage оператор увидит «суммарное состояние объекта» — нужна подписка на все теги объекта.

`object:` и `diagram:` — это серверный fan-out: один subscribe-frame со стороны клиента → разворачивается на N tag-подписок внутри ms-viewer. Клиент при этом всегда получает сообщения формата `value` с конкретным `tag_id` (без нового сообщения per-object — операторам нужно агрегировать самим).

## Files

### Backend (`ms-viewer/internal/`)

#### New files

- `internal/realtime/topic_resolver.go` — `TopicResolver`: `ResolveTopics(ctx, conn, topics) → resolvedSet, errors`. Загружает membership (`object → []tag_id`, `diagram → []tag_id`) из БД (`devices.devices`, `tags.tags`, `public.figures`), кэширует в памяти.
- `internal/realtime/membership_cache.go` — `MembershipCache`: per-entity мапинг и обратный индекс `tag_id → set<entity>` для эффективной инвалидации.
- `internal/realtime/subscription_groups.go` — внутренняя структура: для каждого `Connection` хранит `directTags map[string]struct{}` (явные) и `groupedTopics map[string]map[string]struct{}` (`object:<id>` или `diagram:<id>` → set tag_ids на момент subscribe).

#### Modified files

- `internal/realtime/protocol.go` — расширить тип топика: `tag:<uuid> | object:<uuid> | diagram:<uuid>`.
- `internal/realtime/hub.go`:
  - `Subscribe(conn, topic)` распознаёт префикс, для group-topic’ов вызывает `TopicResolver.ResolveTopics`.
  - `Unsubscribe` корректно работает с group-topic’ами: убирает только те tag-подписки, которые принадлежали этой группе И не входят ни в одну другую активную группу/прямую подписку этого соединения (refcount per-(connection, tag)).
  - При `config.changed` (см. ниже) — пересчитывает membership активных group-подписок и атомарно diff’ит: добавляет subscribe, убирает unsubscribe.
- `internal/usecase/config_change_usecase.go` (из 0032) — после инвалидации `TagMetaCache` вызывает `MembershipCache.Invalidate(entity_type, entity_id)`, который перетряхивает соответствующие group-подписки.
- `internal/api/http/ws.go` — извлечение `roles` из JWT уже есть из 0030; здесь добавить проверку «принадлежит ли пользователь объекту» (заглушка под 0036 — пока пропускаем всех с любой ролью).
- `internal/config/config.go`:
  - `WSGroupResolveLimit` (default 500) — макс. количество tag_id, которое может развернуться из одного group-topic. Превышение → `error: "limit-exceeded"`.

## Interface

### Расширение протокола (server-side parsing)

`subscribe`-frame:
```json
{ "t": "subscribe", "topics": ["tag:UUID", "diagram:UUID", "object:UUID"] }
```

Server resolution (одна транзакция в БД):

| Topic | SQL |
|---|---|
| `tag:<uuid>` | как было — direct |
| `diagram:<uuid>` | `SELECT DISTINCT tag_id FROM public.figures WHERE diagram_id = $1 AND tag_id IS NOT NULL AND deleted_at IS NULL` |
| `object:<uuid>` | `SELECT t.id FROM tags.tags t JOIN devices.devices d ON d.id = t.device_id WHERE d.object_id = $1 AND t.deleted_at IS NULL AND d.deleted_at IS NULL` |

Если `len(resolved) > WSGroupResolveLimit` → `error: { code: "limit-exceeded", topics: ["object:<id>"] }`, эта группа НЕ подписывается; остальные топики из той же команды обрабатываются.

Если diagram/object не существует или soft-deleted → `error: { code: "invalid-topic", topics: [...] }`.

Ответ клиенту: `{ "t": "subscribed", "topics": [...] }` со списком успешно подписанных group-топиков (в исходной форме `diagram:<id>`, не разворачиваем для клиента).

### Membership cache + invalidation

```go
type MembershipCache interface {
    GetDiagramTags(ctx, diagramID) ([]string, error)   // SQL + cache
    GetObjectTags(ctx, objectID) ([]string, error)
    Invalidate(entityType, entityID string)
    InvalidateByTag(tagID string)                       // когда меняется tag.device_id или figure.tag_id
}
```

TTL — 600s (как `TagMetaCache` из 0032). Размер — без LRU-cap (мнемосхем и объектов мало; кэшируем все).

Инвалидация по `config.changed`:
- `entity_type=diagram` → `Invalidate("diagram", entity_id)`.
- `entity_type=figure` → требует `payload.diagram_id` (см. 0032 § Constraints) → `Invalidate("diagram", payload.diagram_id)`.
- `entity_type=tag` → `InvalidateByTag(entity_id)` → перетряхнуть все group-подписки, в которых этот tag может был.
- `entity_type=device` → `Invalidate("object", payload.object_id)` (если payload.object_id есть; иначе invalidate-all для objects).
- `entity_type=object` → `Invalidate("object", entity_id)`.

После инвалидации — для каждого активного `Connection` с group-подпиской на затронутый entity:
1. Перерезолвить топик → новый набор `tag_id`.
2. Diff со старым набором: `added`, `removed`.
3. Для каждого `added` — добавить в Hub-индекс (`tag_id → conn`).
4. Для каждого `removed` — убрать из Hub-индекса (если refcount этого `tag_id` для этого conn упал до 0).
5. Отправить клиенту `{ "t": "topics_changed", "topic": "diagram:<id>", "added_count": N, "removed_count": M }` (информативно; клиент не обязан реагировать).

### Refcount per-(connection, tag)

Один `tag_id` может попасть в подписки соединения через несколько путей:
- direct `tag:<id>`,
- через `diagram:<id>` (одна),
- через `object:<id>` (одна),
- (теоретически) через несколько `diagram:<id>` (фигура из одного тега в нескольких схемах).

Refcount хранится в `Connection.tagRefs map[string]int`. `Subscribe` инкрементит; `Unsubscribe` декрементит; при достижении нуля — реально убирает из Hub-индекса. Это критично, чтобы `unsubscribe object:<id>` не оборвал `tag:<id>`, который оператор подписан напрямую.

### Frontend — обновление DiagramPage

```ts
// было (0031):
const boundTags = computeBoundTags(diagram.figures);
useTagSubscription(boundTags, onValue);

// становится:
useTopicSubscription([`diagram:${diagramId}`], onValue);
```

`useTopicSubscription` — обобщение `useTagSubscription` из 0030, принимает массив строк topic. Внутри — тот же refcount-store.

Сообщения `value` приходят как и раньше (`tag_id` есть в каждом frame), фронт-маршрутизация в `applyDynamics` не меняется.

## Constraints

### Backend

- При `Subscribe(conn, "diagram:<id>")` membership-cache должен быть прогрет (фоновая фоновая загрузка) до возврата `subscribed`. Иначе клиент получит `subscribed` без реальных tag-привязок.
- `topics_changed` сообщения — best-effort; если клиент не справляется (outbox full) — drop oldest, как и `value`-frames.
- Группа `object:<id>` может развернуться в сотни тегов. При `WSMaxSubscriptionsPerConn = 200` (из 0030) проверка лимита считает **уникальные** tag_id (refcount), не «каждое вхождение». То есть если оператор подписан на `tag:<X>` и `diagram:<Y>` (где tag X входит в диаграмму Y), считается как один tag в лимите.
- Нагрузка: в худшем случае при `object_id` с 500 тегами и 100 одновременных операторов на этом объекте — 50K activations в Hub-индексе. Это всё ещё помещается в одну реплику ms-viewer, но если профилирование покажет горячую блокировку RWMutex — переходим к sharded map (отдельная задача).
- При `config.changed` для тега, попавшего в большое количество group-подписок (например, тег «давление в системе» отрисован на 10 мнемосхемах) — все эти подписки получают `topics_changed`, но это event редкий (config меняется минутами/часами).
- DB-доступ для membership: `SELECT` на `public.figures`, `tags.tags`, `devices.devices`. Уже есть в 0029.

### Frontend

- `useTopicSubscription` сохраняет refcount по строке топика (а не по tag-id). Это позволяет двум разным компонентам на одной странице (например, `DiagramScene` + `AlarmTicker`-фильтр на объект) одновременно держать подписку на одну и ту же диаграмму без дублирования.
- При навигации между мнемосхемами одного объекта: `unsubscribe diagram:<old> + subscribe diagram:<new>`. Не подписываемся на `object:<id>` тут — это ширше, чем нужно.
- При size 0 ответа `subscribed` (например, мнемосхема без figures с tag_id) — это валидно, не показываем ошибку; live-tail просто не приедет.
- `error: "limit-exceeded"` обрабатывается с уведомлением «Слишком крупный объект, отображаются не все теги» (Mantine Notification, autoClose 10s).

## Verify

### Backend

- `go test ./internal/realtime/...` — зелёные.
- WS subscribe `["diagram:<id>"]` для мнемосхемы с 5 figures (3 с tag_id) → ответ `subscribed`, после публикации в `tags.values` для одного из этих 3 тегов клиент получает `value`-frame.
- Subscribe одновременно на `tag:<X>` и `diagram:<Y>` (где X ∈ Y): unsubscribe `tag:<X>` → подписка на X **сохраняется** (через diagram). Unsubscribe `diagram:<Y>` → подписка на X **тоже сохраняется** (через direct). Unsubscribe обоих → реально отписан.
- Subscribe на `object:<id>` с 600 тегами при `WSGroupResolveLimit=500` → `error: "limit-exceeded"`.
- В editor добавить новую figure с tag_id в открытую у оператора мнемосхему → через config.changed клиент получает `topics_changed { added_count: 1 }` и сразу начинает получать `value` для этого нового тега без ре-subscribe.
- Удалить figure (config.changed `figure.deleted`) → `topics_changed { removed_count: 1 }`, сообщений по этому tag больше нет (если он не привязан где-то ещё в подписках).
- Переименовать тег `tag.updated` без смены device → ничего не делаем с подписками (membership не изменилось), только `config.changed` уходит клиенту.
- Сменить `tag.device_id` (редкий случай) → membership object’а пересчитывается, оператор подписанный на старый object теряет тег, на новый — получает.
- `go test -race ./internal/realtime/...` чистый.

### Frontend

- `pages/DiagramPage` после правки: в DevTools → Network → WS frames видна **одна** subscribe-команда `["diagram:<id>"]` вместо 30+ tag-команд. Поведение idle-схемы не изменилось.
- Переключение между мнемосхемами одного объекта → один `unsubscribe` + один `subscribe`, отвалов сцены нет.
- Live-обновление figures на DiagramPage по тегу из новой figure (после правки в editor) — без F5 (через `topics_changed` membership-flow).
- Limit-exceeded на dashboard → notification, остальные подписки работают.
