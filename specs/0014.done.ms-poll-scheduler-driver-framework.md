# 0014: ms-poll — планировщик опроса и фреймворк драйверов

## Scope

`ms-poll`. Этот спек добавляет планировщик опроса и абстракцию драйвера. Реальные драйверы (Modbus, SNMP) появятся в спеках 0015 и 0016. Здесь — интерфейсы, scheduler, registry драйверов, обработка отмены и реакция на изменения snapshot'а.
Никаких сетевых вызовов в этом спеке (кроме фейкового драйвера для тестов).

## Context

- Базовая конфигурация: спек [`0013.ready.ms-poll-config-cache.md`](0013.ready.ms-poll-config-cache.md).
- Roadmap Phase 4.1 — фреймворк опроса.
- НФТ scan rates ([`docs/01_Требования/НФТ.md`](../docs/01_Требования/НФТ.md), MVP):
  - электрические/быстрые сигналы — 1 Гц.
  - температура/медленные — 1/60 Гц (раз в минуту).
  - health-check устройства — 1/10 Гц (раз в 10 секунд).
- В MVP мы используем фиксированные scan rate в зависимости от типа сигнала (по `unit_symbol`). Тонкая настройка scan rate per-tag — за пределами этого спека.
- Драйвер живёт в контексте одного устройства. Несколько тегов одного устройства группируются и опрашиваются одним драйвером (батч-чтения подбираются конкретным драйвером в 0015/0016).

## Interface

### Reading

```go
package domain

type Quality string

const (
    QualityGood       Quality = "good"
    QualityBad        Quality = "bad"
    QualityUncertain  Quality = "uncertain"
)

type Reading struct {
    TagID    string
    DeviceID string
    Value    any            // float64 / int64 / bool / string — нормализованное значение (нормализация в 0016)
    RawValue any            // что вернул драйвер до нормализации; nil допустим
    Quality  Quality
    Error    string         // непустое только если Quality != good; короткое читаемое сообщение
    ReadAt   time.Time      // таймстемп считывания у poll-сервиса
}
```

### Driver

```go
package domain

type Driver interface {
    // Read опрашивает все теги устройства одной итерацией.
    // Возвращает по одному Reading на каждый tag из tags.
    // Драйвер сам решает, как батчить запросы (например, по диапазонам Modbus-регистров).
    // Не должен лочиться дольше, чем cmd context разрешает.
    Read(ctx context.Context, tags []*TagSnapshot) []Reading

    // HealthCheck — лёгкая проверка доступности устройства (например, чтение одного регистра).
    // Если HealthCheck возвращает ошибку, scheduler пропускает следующий Read до восстановления.
    HealthCheck(ctx context.Context) error

    // Close освобождает ресурсы (TCP-сокеты, serial-порт, SNMP сессию).
    Close() error
}

type DriverFactory interface {
    // Build строит драйвер для конкретного устройства из snapshot.
    // Драйвер привязан к этому устройству — при изменении settings driver пересоздаётся.
    Build(device *DeviceSnapshot) (Driver, error)

    // SupportedType возвращает строку из devices.device_type.name (modbus_tcp, snmp_v2c, ...).
    SupportedType() string
}
```

### DriverRegistry

```go
package usecase

type DriverRegistry struct { /* map[string]domain.DriverFactory */ }

func NewDriverRegistry() *DriverRegistry
func (r *DriverRegistry) Register(factory domain.DriverFactory)
func (r *DriverRegistry) Build(device *domain.DeviceSnapshot) (domain.Driver, error)
```

`Build` ищет фабрику по `device.TypeName`. Если фабрика не найдена — возвращает ошибку `unsupported device type: <type>`. В логе scheduler это превращается в warning, устройство пропускается (без падения сервиса).

В этом спеке регистрируем `noopFactory`, который возвращает драйвер с пустым массивом Reading. Так сервис может стартовать без реальных драйверов.

### Scan rate

```go
package usecase

func ScanRateFor(tag *domain.TagSnapshot) time.Duration
```

Правила:

- `unit_symbol` ∈ {`°C`, `°F`, `K`} → 60 секунд.
- иначе → 1 секунда.
- Health-check — фиксировано 10 секунд (см. ниже scheduler), не зависит от тегов.

(Точные правила вынесены отдельной функцией, чтобы их легко было переопределить или вынести в БД.)

### SnapshotStore subscription

Расширение `SnapshotStore` из 0013:

```go
type SnapshotEvent struct {
    Kind     string  // "replaced" | "device_upserted" | "device_removed" | "tag_upserted" | "tag_removed"
    DeviceID string  // пусто для "replaced"
    TagID    string  // только для tag_*
}

func (s *SnapshotStore) Subscribe() <-chan SnapshotEvent
func (s *SnapshotStore) Unsubscribe(ch <-chan SnapshotEvent)
```

- Канал буферизированный (cap=64). Если переполнился — событие дропается с лог.warning, подписчик должен делать `store.Get()` после дропа на reconciliation.
- Ровно один event на одну мутацию.

### Scheduler

```go
package usecase

type Scheduler struct { /* store, registry, logger */ }

func NewScheduler(
    store *SnapshotStore,
    registry *DriverRegistry,
    publisher TagValuesPublisher, // интерфейс из спека 0016. На 0014 этапе — заглушка.
    logger *slog.Logger,
) *Scheduler

func (s *Scheduler) Run(ctx context.Context) error
```

`TagValuesPublisher` — интерфейс из этого пакета (на 0014 этапе):

```go
type TagValuesPublisher interface {
    Publish(ctx context.Context, readings []domain.Reading) error
}
```

В `cmd/ms-poll/main.go` пока передаём заглушку, которая просто логирует количество readings на уровне `debug`. Реальная имплементация — в 0016.

#### Поведение `Scheduler.Run`

1. Подписаться на snapshot store.
2. Прочитать текущий snapshot и для каждого устройства, у которого есть теги, запустить `runDevice(ctx, deviceID)` в отдельной goroutine. Сохранить `cancel` функции в `map[string]context.CancelFunc`.
3. В цикле слушать:
   - `<-ctx.Done()` → отменить все device goroutine, дождаться их завершения, выйти.
   - `event := <-store.Subscribe()`:
     - `device_upserted`: остановить старую goroutine (если была) и запустить новую.
     - `device_removed`: остановить goroutine.
     - `tag_*`: дёрнуть «soft restart» соответствующего device goroutine (пересоздать drivер, чтобы он увидел новый список тегов). Простейший вариант — отменить и перезапустить.
     - `replaced`: полная переинициализация (как при старте).

#### Поведение `runDevice(ctx, deviceID)`

Жизненный цикл одного устройства:

1. Получить snapshot устройства и теги через `store.Get()`.
2. Сгруппировать теги по `ScanRateFor(tag)`. Получится N групп (на MVP — обычно 1–2).
3. Через `registry.Build(device)` создать драйвер. При ошибке: лог warning, ждать 30 сек и retry; продолжать ждать, пока ctx не отменён.
4. Запустить:
   - tickers по каждой группе (`time.NewTicker(rate)`); на каждый tick вызвать `driver.Read(ctx, groupTags)` → `publisher.Publish(...)` пачкой.
   - health ticker `time.NewTicker(10*time.Second)` → `driver.HealthCheck(ctx)`. При неуспехе помечать device unhealthy: пропускать следующие Read циклы до тех пор, пока HealthCheck не вернёт `nil` подряд один раз.
5. По `ctx.Done()`: остановить тикеры, `driver.Close()`, выйти.

Все обращения к driver — синхронные. Если `Read` дольше, чем scan rate, следующий tick дропается (стандартное поведение `time.Ticker`).

#### Concurrency правила

- Разные устройства — независимые goroutine.
- Внутри одного устройства — ОДНА goroutine, последовательные Read и HealthCheck (для serial RTU это критично — спек 0015 будет дополнительно сериализовать по serial-порту, но scheduler об этом не знает).
- `publisher.Publish` ВСЕГДА вызывается из device goroutine — никаких отдельных пулов.

## Constraints

- Никаких реальных сетевых вызовов в этом спеке — только заглушечный `noopFactory` и интерфейсы.
- `Driver.Read` НЕ должен возвращать ошибку — все ошибки оформляются как `Reading{Quality: bad, Error: "..."}` per-tag. Это упрощает scheduler (он только агрегирует).
- `HealthCheck` — единственное место, где драйвер может возвращать `error`. Это используется только для пропуска опроса, не для рестарта драйвера.
- `runDevice` НЕ паникует. Любая ошибка → лог + retry/skip.
- `TagValuesPublisher` объявлен интерфейсом в `usecase`, чтобы 0016 имплементировал его в `infrastructure/kafka` без циклической зависимости.
- Один scheduler на процесс. Никаких сложных пулов / шарингов в MVP.
- При перезагрузке устройства scheduler **закрывает** старый драйвер перед запуском нового, не плодит TCP-сокеты.
- Не вводить metrics/Prometheus — это отдельная задача (Phase 4.8). Только логи на уровне `debug`/`info`/`warn`/`error`.

- `cd ms-poll && go build ./... && go vet ./...` зелёное.
- Юнит-тесты `ms-poll/internal/usecase/scheduler_test.go` с `fakeDriver`:
  - device без тегов не порождает goroutine.
  - device с двумя тегами разных scan rates получает два тика разной частоты.
  - `device_removed` останавливает goroutine (`fakeDriver.Close()` вызван ровно 1 раз).
  - `device_upserted` с изменёнными settings перестраивает драйвер (старый Close + новый Build).
  - `tag_removed` приводит к рестарту device goroutine с уменьшенным набором тегов.
  - HealthCheck error пропускает следующий Read цикл; HealthCheck OK возобновляет.
  - При `ctx.Done()` все драйверы закрыты, goroutine завершены (`runtime.NumGoroutine` стабилизируется).
- Юнит-тест `ms-poll/internal/usecase/scan_rate_test.go`:
  - Tag c `unit_symbol=°C` → 60s.
  - Tag c `unit_symbol=V` → 1s.
  - Tag c `unit_symbol=nil` → 1s.
- Запуск `go run ./cmd/ms-poll` со snapshot из БД, в котором есть устройства типа `modbus_tcp`:
  - В логе `scheduler started`, для каждого устройства `device started device_id=... tags=N driver=noop`.
  - При удалении устройства через ms-editor: `device removed device_id=...` + `device stopped device_id=...`.
  - При SIGTERM: все `device stopped` логируются перед `scheduler stopped`.
