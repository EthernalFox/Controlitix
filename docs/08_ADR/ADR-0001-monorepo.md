# ADR-0001: Монорепозиторий для всех сервисов и фронтендов

- Статус: accepted
- Дата: 2026-04-15
- Авторы: команда Controlitix

## Контекст

Controlitix состоит из нескольких backend-сервисов (`ms-editor`, `ms-poll`, `ms-viewer`, `ms-auth`) и двух фронтендов (`editor-ui`, `viewer-ui`). Все они разрабатываются одной небольшой командой и выпускаются синхронно как единый продукт. Необходимо выбрать схему организации кода.

## Рассмотренные варианты

1. **Монорепозиторий** — все сервисы и фронтенды в одном Git-репозитории, общая документация в `docs/`.
2. **Polyrepo** — отдельный репозиторий на каждый сервис и фронтенд, общая документация в отдельном репозитории.
3. **Гибрид** — отдельные репозитории на сервисы, общая документация внутри репозитория ms-editor.

## Решение

Выбран **монорепозиторий**. Структура верхнего уровня:

- `docs/` — документация продукта и архитектуры (источник правды для контрактов).
- `ms-editor/`, `ms-poll/`, `ms-viewer/`, `ms-auth/` — backend-сервисы (Go).
- `editor-ui/`, `viewer-ui/` — фронтенды (React + TypeScript).

## Последствия

**Позитивно:**

- Одно место изменений: PR, затрагивающий API-контракт и его реализацию в нескольких сервисах, живёт в одном коммите.
- Документация всегда под рукой, редактируется вместе с кодом, не дрейфует.
- Проще синхронные релизы (MVP выпускается целиком).
- Единый CI, один набор инструментов линтинга/форматирования.

**Негативно:**

- История репозитория растёт быстрее.
- Нужна дисциплина при структурировании — иначе легко нарушить границы между сервисами.
- Для open-source отдельных компонентов (если понадобится) придётся вырезать поддиректории.
