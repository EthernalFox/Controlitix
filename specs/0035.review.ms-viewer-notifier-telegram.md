# 0035: ms-viewer — Notifier (Telegram), потребление `alarms.events`

## Scope

`ms-viewer/internal/`:

1. Миграция `auth.telegram_chats` (`auth`-схема — владелец `ms-auth`; миграция выполняется в репозитории `ms-auth`, см. § Constraints).
2. Kafka-consumer `alarms.events` (выходного топика 0033) — отдельная consumer-group `ms-viewer-notifier`.
3. Routing: alarm-event → список chat_id → формирование сообщения → отправка через Telegram Bot API.
4. Retry / dedup / escalation policy.
5. Минимальный admin REST: `GET /api/notifier/chats` (для отладки списка bind’ов; редактирование — TBD в admin-плоскости).

Out of scope: UI управления подписками (это отдельная админка), webhook’и других мессенджеров (Slack/Email — за scope MVP).

Зависимости: 0023 (admin/service tokens), 0029, 0033.

## Interface

### Routing

```go
func (uc *NotifierUseCase) RouteAndSend(ctx context.Context, ev domain.AlarmEvent) error
```

Логика:

1. Из `ev` извлечь `tag_id`, `state_to`, `object_id` (через `TagMetaCache` из 0032 или прямой запрос к `tags.tags`/`devices.devices`/etc.).
2. Перевести `state_to` в severity:
   - `hi/lo` → severity 2.
   - `hihi/lolo` → severity 4.
   - `comm_loss/offline/bad/uncertain` → severity 3.
   - `ok` (event_type=cleared) → severity 1.
   - `acked` (event_type=acked) → severity 1, но шлём отдельный шаблон.
3. Загрузить `auth.telegram_chats WHERE enabled = true AND severity_min <= $1 AND (object_id IS NULL OR object_id = $2)`.
4. Для каждого chat:
   - `INSERT INTO alarms.notifications (alarm_event_id, chat_id, status=0, attempt=0)` (`ON CONFLICT DO NOTHING` — dedup по `(event, chat)`).
   - Сразу попытка отправки: `Send(chat, message)`. Успех → `UPDATE status=1, sent_at=now()`. Сбой → `UPDATE status=0, attempt=1, last_error=...`.
5. Для `event_type=raised` с severity=4 (hihi/lolo) — поставить в очередь escalation-задачу (через `NotifierEscalationDelaySec`).

### Retry-сканер

Goroutine каждые `NotifierBatchPollSec` секунд:
1. `SELECT id, alarm_event_id, chat_id, attempt FROM alarms.notifications WHERE status=0 AND attempt < $1 AND updated_at < now() - INTERVAL 'X seconds'` (X = backoff(attempt)).
2. Для каждой — повторная отправка; на успех/финальный fail обновить статус.
3. Limit batch 100 за тик.

### Escalation

Если для alarm-event сохранилось state=hihi/lolo и нет ack в течение `NotifierEscalationDelaySec`:
- Найти `auth.telegram_chats WHERE role = 'admin' AND enabled = true AND (object_id IS NULL OR object_id = $1)`.
- Послать `escalation`-шаблон (тот же event, но с пометкой «Не квитировано N минут»).
- Записать как обычное `alarms.notifications` с теми же dedup-правилами.

Реализация: при `RouteAndSend` event=raised severity=4 → ставим запись в отдельную таблицу `alarms.escalations { alarm_event_id, fire_at, processed }` (миграция). Сканер каждые 30s проверяет `fire_at <= now() AND processed = false`. Если за это время был ack (`alarms.acks` для этого `tag_id` с `state >= state_to`), эскалация отменяется (`processed = true, skipped`).

Миграция таблицы `alarms.escalations`:
```sql
CREATE TABLE alarms.escalations (
    id              uuid PRIMARY KEY DEFAULT gen_random_uuid(),
    alarm_event_id  uuid NOT NULL,
    tag_id          uuid NOT NULL,
    state           smallint NOT NULL,
    fire_at         timestamptz NOT NULL,
    processed       boolean NOT NULL DEFAULT false,
    skipped         boolean NOT NULL DEFAULT false,
    created_at      timestamptz NOT NULL DEFAULT now()
);

CREATE INDEX escalations_due_idx ON alarms.escalations (fire_at) WHERE processed = false;
```

### Telegram client

```go
type Client interface {
    SendMessage(ctx context.Context, chatID int64, text string, parseMode ParseMode) error
}
```

Реализация:
- `POST {API}/bot{TOKEN}/sendMessage` JSON body `{chat_id, text, parse_mode, disable_web_page_preview: true}`.
- Тайм-аут: `TelegramRequestTimeoutSec`.
- Retry в самом client’е — НЕТ (повторы — на уровне scheduler’а, чтобы переживать рестарты сервиса).
- Обработка `429 Too Many Requests`: respect `Retry-After` через `RateLimitError{retryAfter}`. Notifier scheduler уважает.
- 4xx (кроме 429) → `PermanentError`; статус notification → `failed` без retry.
- 5xx / network → `TransientError`; retry по обычной схеме.

## Constraints

- `TELEGRAM_BOT_TOKEN` — секрет; никогда не логировать. В config-логе на старте — выводить `set/unset`, не значение.
- Если `TelegramBotToken == ""` — notifier стартует, но в режиме «dry-run»: события из Kafka потребляются и парсятся, но `Client.SendMessage` заменяется на лог-only fake. Это для dev-сред без telegram.
- Notifier consumer-group `ms-viewer-notifier` отдельная от `ms-viewer-config-changed` и `ms-viewer-tags-values`. Любой failure не блокирует ingest или alarms-engine.
- Идемпотентность критична: при перезапуске сервиса Kafka может переотдать событие; уникальный `(alarm_event_id, chat_id)` гарантирует «не больше одного сообщения в чат на одно событие».
- Markdown V2: все динамические подстановки (имена объектов, теги) экранируются. Утилита `telegramEscape(s)` — отдельный helper, тестируется на специальных символах `_*[]()~\`>#+-=|{}.!`.
- Retry-backoff с jitter (random ±20%) — иначе при массовой эскалации все попытки идут синхронно.
- Telegram rate limits (≤ 30 messages per second глобально на bot, ≤ 1 message per second per chat) — учитывать в client’е через token-bucket. Простой подход для MVP: глобальный sleep `33ms` между подряд идущими сообщениями. Profile-driven оптимизация — потом.
- DB-роль `ms_viewer`: `SELECT` на `auth.telegram_chats`; `INSERT/SELECT/UPDATE` на `alarms.notifications`, `alarms.escalations`.
- Логирование: `notifier.sent{chat_id, alarm_event_id, attempt, latency_ms}`, `notifier.failed{...,error}`, `notifier.skipped{reason}`. Не логировать содержимое сообщения.
- Cron-сканер для retry/escalation — НЕ внешний cron, а goroutine внутри сервиса. На несколько реплик ms-viewer добавится защита (advisory-lock в PG `pg_try_advisory_lock(NOTIFIER_SCHEDULER_LOCK_KEY)`), чтобы только одна реплика обрабатывала очередь.
- На graceful shutdown: дослать pending pending → если за 5s не успели — оставить в БД, при старте сканер их подберёт.

### 1. Двойной backslash в `telegramEscape` ломает MarkdownV2 (баг)

Файл: `ms-viewer/internal/infrastructure/telegram/templates.go:128-155`.

`strings.NewReplacer` сейчас инициализируется raw-строками с `\\<char>`, что даёт литеральные **два** backslash перед каждым спецсимволом, а MarkdownV2 ожидает **один**:

```go
// сейчас (raw-string `\\_` = 3 байта: '\', '\', '_'):
replacer := strings.NewReplacer(
    `\\`, `\\\\`,
    `_`, `\\_`,
    `*`, `\\*`,
    ...
)
```

В результате имя `boil_1.t_(out)` уходит в Telegram как `boil\\_1\\.t\\_\\(out\\)`, и API возвращает `400 Bad Request: can't parse entities: Character '\' is reserved...` либо рендерит литеральные `\` в сообщении.

Исправить — заменить raw-строки на интерпретируемые двойные кавычки **или** оставить raw, но с одним backslash. Минимальная правка:

```go
replacer := strings.NewReplacer(
    "\\", "\\\\",   // backslash → \\
    "_", "\\_",
    "*", "\\*",
    "[", "\\[",
    "]", "\\]",
    "(", "\\(",
    ")", "\\)",
    "~", "\\~",
    "`", "\\`",
    ">", "\\>",
    "#", "\\#",
    "+", "\\+",
    "-", "\\-",
    "=", "\\=",
    "|", "\\|",
    "{", "\\{",
    "}", "\\}",
    ".", "\\.",
    "!", "\\!",
)
```

Добавить unit-тест (нет в `templates_test.go`?), который проверяет: `telegramEscape("a.b_c")` == `"a\.b\_c"` (3 escape-последовательности, 6 байт + ещё текст). Без этого регрессия повторится.

### 3. Consumer убивает себя на любой ошибке `RouteAndSend` (риск стоп-мира notifier’а)

Файл: `ms-viewer/internal/infrastructure/kafka/alarms_consumer.go:98-112`.

```go
handleError := consumer.handler.RouteAndSend(ctx, event)
if handleError != nil {
    consumer.logger.Error(...)
    return fmt.Errorf("handle alarm event: %w", handleError)   // выходим из Run, останавливая consumer
}
```

`RouteAndSend` возвращает ошибку при недоступности БД (`GetAlarmRouteContext`, `ListChatsForRouting`, `CreateNotification`). Любой временный сбой PG → весь notifier-consumer падает, и его перезапуск возможен только полным рестартом сервиса; offsets не коммитятся, но новые `alarms.events` не обрабатываются вообще.

Спека (§ Constraints) фиксирует: «Notifier consumer-group `ms-viewer-notifier` отдельная … любой failure не блокирует ingest или alarms-engine». Сейчас не блокирует только ingest, но блокирует **сам себя**.

Исправить — на ошибке `RouteAndSend` логировать ERROR и продолжать цикл **без** коммита оффсета (Kafka повторно отдаст сообщение на следующей итерации/после rebalance). Идемпотентность гарантирована UNIQUE `(alarm_event_id, chat_id)` в `alarms.notifications`. Минимальная правка:

```go
handleError := consumer.handler.RouteAndSend(ctx, event)
if handleError != nil {
    consumer.logger.Error(
        "failed to handle alarm event",
        "method", "AlarmsConsumer.Run",
        "alarm_event_id", event.ID.String(),
        "tag_id", event.TagID.String(),
        "error", handleError,
    )
    // не коммитим offset → Kafka переотдаст сообщение; idempotency защищает от дублей
    continue
}
```

Альтернатива (если хочется более строго): добавить метрический счётчик `notifier.handler_errors_total` и rate-limit на повторы (повторять не каждый цикл fetch, а с экспоненциальным backoff), но для MVP `continue` достаточно.
