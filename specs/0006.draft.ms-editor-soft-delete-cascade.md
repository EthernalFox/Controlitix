# 0006: ms-editor — Soft delete + cascade

## Scope

`ms-editor/internal/` — domain, usecase, infrastructure/repository.

## Context

Entities must support soft delete (`deleted_at` column) with cascading logic:
- Deleting an **object** → soft-deletes its devices, their tags, its diagrams, their figures.
- Deleting a **device** → soft-deletes its tags.
- Deleting a **diagram** → soft-deletes its figures.

Migration 000002 (spec 0002) already added `deleted_at` columns. Specs 0003/0004 already filter by `deleted_at IS NULL` in reads and set `deleted_at = now()` on individual deletes. This spec adds the **cascade logic** and ensures consistency across all entities.

Prerequisite: specs 0002, 0003, 0004.

## Files

### Modified files

- `ms-editor/internal/usecase/monitoring_object_usecase.go` — cascade delete to devices + diagrams
- `ms-editor/internal/usecase/device_usecase.go` — cascade delete to tags
- `ms-editor/internal/usecase/diagram_usecase.go` — cascade delete to figures
- `ms-editor/internal/domain/repository.go` — add cascade-oriented methods if needed
- `ms-editor/internal/infrastructure/repository/postgres_repository.go` — implement cascade SQL

## Cascade rules

### Object delete

When `DeleteMonitoringObject(objectID)` is called:

1. Soft-delete all **devices** where `object_id = objectID AND deleted_at IS NULL`.
2. For each such device, soft-delete all **tags** where `device_id = device.id AND deleted_at IS NULL`.
3. Soft-delete all **diagrams** where `object_id = objectID AND deleted_at IS NULL`.
4. For each such diagram, soft-delete all **figures** where `diagram_id = diagram.id AND deleted_at IS NULL`.
5. Soft-delete the **object** itself.

All operations in a single database transaction.

### Device delete

When `DeleteDevice(deviceID)` is called:

1. Soft-delete all **tags** where `device_id = deviceID AND deleted_at IS NULL`.
2. Soft-delete the **device** itself.

Single transaction.

### Diagram delete

When `DeleteDiagram(diagramID)` is called:

1. Soft-delete all **figures** where `diagram_id = diagramID AND deleted_at IS NULL`.
2. Soft-delete the **diagram** itself.

Single transaction.

### Tag delete

No cascade — tags have no children. Just set `deleted_at = now()`.

### Figure delete

No cascade — figures have no children. Just set `deleted_at = now()`.

## Interface

### New repository methods (or update existing)

```go
// Option A: batch soft-delete methods in each repository
type DeviceRepository interface {
    // ... existing ...
    SoftDeleteByObjectID(ctx context.Context, tx *sql.Tx, objectID string) (int, error)
}

type TagRepository interface {
    // ... existing ...
    SoftDeleteByDeviceID(ctx context.Context, tx *sql.Tx, deviceID string) (int, error)
    SoftDeleteByDeviceIDs(ctx context.Context, tx *sql.Tx, deviceIDs []string) (int, error)
}

type FigureRepository interface {
    // ... existing ...
    SoftDeleteByDiagramID(ctx context.Context, tx *sql.Tx, diagramID string) (int, error)
    SoftDeleteByDiagramIDs(ctx context.Context, tx *sql.Tx, diagramIDs []string) (int, error)
}

type DiagramRepository interface {
    // ... existing ...
    SoftDeleteByObjectID(ctx context.Context, tx *sql.Tx, objectID string) (int, error)
}
```

**Alternative**: implement cascade entirely in SQL using CTEs or multiple UPDATE statements within one transaction, without separate batch methods. Choose whichever is cleaner — the important thing is atomicity.

### Transaction support

The `PostgresRepository` needs a way to run multiple operations in a single transaction. Options:

- (A) Add a `WithTransaction(ctx, fn func(tx) error) error` method on the repository.
- (B) Use `database/sql` `Tx` and pass it through context.
- (C) Implement cascade as a single SQL statement with CTEs.

Choose the approach that fits the existing codebase best. Option (A) is recommended as it's the most Go-idiomatic for Clean Architecture.

## Constraints

- All cascade operations MUST be atomic (single transaction).
- `deleted_at` is set to `now()` (database time), not application time.
- Cascade does NOT emit Kafka events for each child entity — only the root event is published. For example, deleting an object emits one `config.changed` event with `entity_type: "object"`, `operation: "deleted"`. Consumers must handle the cascade inference.
- Already soft-deleted children are NOT affected (use `WHERE deleted_at IS NULL` in cascade updates).
- Return counts of affected rows in log messages for observability.
- Do not add restore/undelete functionality in this spec.

## Kafka events on cascade

| Action | Event emitted |
|--------|--------------|
| Delete object | `config.changed { entity_type: "object", operation: "deleted" }` |
| Delete device | `config.changed { entity_type: "device", operation: "deleted" }` |
| Delete diagram | `config.changed { entity_type: "diagram", operation: "deleted" }` |
| Delete tag | `config.changed { entity_type: "tag", operation: "deleted" }` |
| Delete figure | `config.changed { entity_type: "figure", operation: "deleted" }` |

Child entities do NOT get separate events when deleted via cascade.

## Verify

- `go build ./...` passes.
- Create object → create 2 devices with tags → create diagram with figures.
- `DELETE /objects/{id}` → object, both devices, all tags, diagram, all figures have `deleted_at IS NOT NULL` in DB.
- All subsequent `GET` calls for these entities return 404.
- List endpoints no longer include soft-deleted entities.
- Create device with tags → `DELETE /devices/{id}` → device and tags are soft-deleted.
- Create diagram with figures → `DELETE /diagrams/{id}` → diagram and figures are soft-deleted.
- Verify atomicity: if the DB transaction fails mid-cascade, nothing is deleted (rollback).
- Only one Kafka event emitted per delete action (not per child entity).
