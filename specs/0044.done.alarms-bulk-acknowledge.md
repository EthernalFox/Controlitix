# 0044: ms-viewer + viewer-ui — Групповое квитирование тревог

## Scope

**Backend (`ms-viewer`)**:
- Новый эндпоинт `POST /api/alarms/acknowledge` (массовый ack массива `tag_id`).
- Транзакционная обработка с per-item статусом (success / not-active / not-found).
- Один Kafka-batch + один WS-broadcast по итогу транзакции.

**Frontend (`viewer-ui`)**:
- Расширение `pages/AlarmsPage` (из 0033): чекбоксы, выбор-всё-в-фильтре, кнопка «Квитировать выделенные», модалка с комментарием, обработка частичного успеха.

Out of scope: отдельный эндпоинт «квитировать все по объекту/severity/фильтру». Это надстройка над массовым `tag_id[]`-эндпоинтом — клиент сам собирает список из текущей выборки.

## Context

Phase 6.4 роадмапа: «Мульти-выделение (чекбоксы). Кнопка «Квитировать выделенные» (групповое)».

Спека 0033 поставила одиночный ack `POST /api/alarms/{tagId}/acknowledge`. Этого недостаточно для типичной картины «после ночного сбоя 30 тревог по объекту» — оператору нужно квитировать пачкой, с одной отметкой времени и одним комментарием.

Архитектурно: одиночный эндпоинт остаётся (точка в URL — `tagId` в path), массовый — отдельный URL без `tagId` в path. Это явно разные операции, не путаем формы запроса.

## Interface

### Backend — DTO

```go
// alarm_models.go
type BulkAckRequestItem struct {
    TagID string `json:"tag_id"`
}

type BulkAckRequest struct {
    Items []BulkAckRequestItem `json:"items"`     // 1..200
    Note  *string              `json:"note,omitempty"`
}

type BulkAckItemResult struct {
    TagID  string  `json:"tag_id"`
    Status string  `json:"status"`         // "acked" | "not_active" | "not_found" | "already_acked"
    State  *string `json:"state,omitempty"` // на acked — текущее состояние
}

type BulkAckResponse struct {
    Items     []BulkAckItemResult `json:"items"`
    AckedAt   time.Time           `json:"acked_at"`
    ActorID   string              `json:"actor_id"`
    SuccessN  int                 `json:"success_n"`
    FailedN   int                 `json:"failed_n"`
}
```

### Backend — поведение

`POST /api/alarms/acknowledge` body `BulkAckRequest`:

1. **Валидация:**
   - `len(Items) ∈ [1, 200]`. Иначе → 422 `/errors/alarms/bulk-size`.
   - Дедупликация по `TagID` на входе (молча, без ошибки).
   - `Note` ≤ 500 символов. Иначе → 422.

2. **Транзакция** (`SERIALIZABLE` не нужен, `READ COMMITTED` достаточно — мы не читаем-после-update в этой же tx’е):
   - `SELECT tag_id, state FROM alarms.states WHERE tag_id = ANY($1) FOR UPDATE` — единым запросом.
   - Для каждого `tagID` из запроса:
     - Нет в states → result `not_found`.
     - `state == 0` → result `not_active`.
     - Уже есть в `alarms.acks` с тем же `state` → result `already_acked` (не пишем повторно, но НЕ откатываем транзакцию).
     - Иначе:
       - `INSERT INTO alarms.acks (tag_id, state, actor_id, note, acked_at)` (или UPSERT при существующем acks с другим state — обновляем).
       - `INSERT INTO alarms.events (tag_id, event_type=acked, state_from=state, state_to=state, actor_id, note, ts=now())`.
       - result `acked`.
   - Commit.

3. **Постобработка** (вне транзакции):
   - Собрать `events []AlarmEvent` для всех `acked`-результатов.
   - Один `kafka.PublishBatch(events)` (best-effort, не блокирует ответ — ретрай-фоном при ошибке).
   - Один `hub.BroadcastAlarmBatch(events)` через WS-сообщение `alarms_batch`.

4. **HTTP-статус ответа:**
   - Все `acked` → `200 OK`.
   - Хотя бы один не-acked + хотя бы один acked → `207 Multi-Status`.
   - Все элементы fail → `409 Conflict` (тело — то же `BulkAckResponse`, `success_n=0`).

### Backend — Kafka batch

`alarms_producer.PublishBatch`:

- Каждое событие — отдельный record в Kafka, key = `tag_id` (как и в одиночном publish из 0033).
- Использовать sync-producer с одним `Flush(timeout=5s)` в конце цикла. Если flush failed — логируем (`level=error`, `events_n`, причина) и перекладываем events в retry-очередь (in-memory, бессрочный retry до рестарта). На MVP не персистируем retry — допустимая потеря в случае краша процесса (соответствует 0033 § Constraints).

### Backend — WS broadcast

```json
{
  "t": "alarms_batch",
  "ts": "2026-04-30T10:01:00.123Z",
  "events": [
    { "event_type": "acked", "tag_id": "...", "state_from": "hi", "state_to": "hi", "actor_id": "...", "note": "Принято в работу", "ts": "..." },
    { "event_type": "acked", "tag_id": "...", ... }
  ]
}
```

Один frame на батч; клиент применяет все `events` атомарно. Это снижает дребезг для подписчиков, наблюдающих 50 строк одновременно.

Совместимость с 0033: одиночные операции продолжают слать `{ "t": "alarm", ...event }`. Клиент должен уметь оба формата.

### Frontend — выбор и реконсиляция

```ts
// pages/AlarmsPage
const [selected, setSelected] = useState<Set<string>>(new Set());

// При изменении items (фильтры или WS-обновление):
useEffect(() => {
  const visibleIds = new Set(items.filter(i => isAckable(i)).map(i => i.tag_id));
  setSelected(prev => new Set([...prev].filter(id => visibleIds.has(id))));
}, [items]);
```

`isAckable(item)`: `state > 0 && !item.acked`.

Master-чекбокс в шапке:
- `checked` если все `ackable` строки выбраны.
- `indeterminate` если выбрано подмножество.
- Click toggle на всё ackable в текущем фильтре.

### Frontend — flow подтверждения

1. Click «Квитировать выделенные» (disabled если `selected.size === 0`).
2. Модалка `AlarmsBulkAckModal`:
   - Заголовок «Квитировать N тревог».
   - Опциональное поле «Комментарий» (textarea, max 500).
   - Collapsible-блок «Список тегов» (по умолчанию свёрнут; `tag_name` + `device_name`).
   - Primary-кнопка «Квитировать» с лоадером во время запроса.
3. Submit: `acknowledgeBulk([...selected], note)`:
   - **Optimistic:** для всех `selected` сразу `acked: true` локально, mute строк (полупрозрачность).
   - POST.
   - На ответ:
     - Все `acked` → строки убираются из активных (если `status=active` фильтр); Notification «Квитировано N тревог».
     - 207 mixed → реконсиляция: для `not_active`/`not_found`/`already_acked` — откат optimistic-pomethy, Notification предупреждения «N квитировано, M не удалось» с возможностью раскрыть детали.
     - Сетевая ошибка / 5xx → полный откат, Notification ошибки.
4. После закрытия модалки — `selected.clear()`.

### Errors (RFC 7807)

| Type | Status |
|---|---|
| `/errors/alarms/bulk-size` | 422 |
| `/errors/alarms/note-too-long` | 422 |

Per-item ошибки **не** превращаются в 4xx HTTP — они идут в теле как item.status.

## Constraints

### Backend

- Лимит 200 на батч — защита от случайного «выбрать все 5000» и от долгой транзакции. Если оператору нужно больше — разбивает клиент.
- Транзакция должна быть короткой: `FOR UPDATE` блокирует строки `alarms.states`; параллельный ingest по этим тегам ждёт. На 200 тегов это десятки миллисекунд — приемлемо.
- При смешанном результате коммитим успешные ack’и. Не делать all-or-nothing: оператор не должен из-за одного «уже квитированного» терять ack 199 остальных.
- Kafka-публикация — после commit. Порядок: `tx.Commit()` → `kafka.PublishBatch()` → `hub.BroadcastAlarmBatch()`. Принцип тот же, что в 0033.
- Если Kafka publish неуспешен — ack уже в БД. Это соответствует политике 0033 («persistence first, downstream best-effort»).
- WS broadcast — fire-and-forget. Если клиент отстал — drop oldest (общая политика Hub из 0030).
- Аудит: `actor_id` в каждом event берём из `principal.subject` (JWT `sub`). Без него запрос отклоняется на уровне `RequireAuth` middleware (это и так есть из 0024).
- Идемпотентность по item: повторная попытка `acknowledgeBulk` с тем же набором → второй раз все придут `already_acked`, БД не меняется, Kafka/WS не публикуем (так как `acked.length == 0`). Это безопасно для retry на стороне клиента.
- БД-роль `ms_viewer` — права те же, что в 0033 (`INSERT/SELECT/UPDATE/DELETE` на `alarms.*`). Новых grant’ов не нужно.

### Frontend

- Чекбокс не появляется на не-ackable строках (cleared, уже acked) — серая зона `td`, не disabled-чекбокс. Меньше шумных кликов.
- Если оператор переключает фильтр (например, на `acked`) — `selected` чистится автоматически (через useEffect выше).
- Модалка не закрывается по клику вне неё во время submit (предотвращаем двойной submit).
- На 207 — Notification остаётся открытым (`autoClose: false`) до закрытия пользователем; на 200 — autoClose 4s.
- Никаких прямых импортов `@mantine/core` в `pages/AlarmsPage` или `widgets/AlarmsBulkAckModal`. Только через `shared/ui/components`.
- `comment` — поле tag-name `<Textarea>` фасадное. Не `<TextInput>` (комментарий бывает многострочный).
- Мастер-чекбокс не «выбрать все на сервере», только «всё в текущей странице/фильтре». На MVP это соответствует ожиданию — серверная пагинация ставится в фокус позже.
