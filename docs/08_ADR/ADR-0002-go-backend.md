# ADR-0002: Go как язык backend-сервисов

- Статус: accepted
- Дата: 2026-04-15
- Авторы: команда Controlitix

## Контекст

Нужен язык для backend-сервисов Controlitix: `ms-editor`, `ms-poll`, `ms-viewer`, `ms-auth`. Сервисы решают разные задачи — REST/CRUD, опрос устройств по Modbus/SNMP, обработку потока значений, WebSocket-стриминг, интеграцию с Kafka/PostgreSQL/Redis. Требуется единый стек для снижения сложности.

## Рассмотренные варианты

1. **Go** — статически типизированный, быстрый старт, хорошие библиотеки для Modbus/SNMP/Kafka, низкое потребление памяти, простое развёртывание одним бинарём.
2. **Python** — быстрое прототипирование, хорошая экосистема, но хуже по производительности и потреблению памяти на potoк 2000+ значений/с.
3. **Rust** — лучший по производительности, но порог входа выше, меньше готовых библиотек для SCADA-протоколов, замедлит MVP.
4. **Java/Kotlin** — зрелая экосистема, но тяжёлая память и сложнее упаковывать в малые контейнеры.
5. **Node.js** — хорош для I/O-задач, но хуже для длительного опроса устройств и потоковой обработки.

## Решение

Выбран **Go** для всех backend-сервисов.

Обоснование:

- Низкое потребление памяти критично для self-hosted инсталляции на одном хосте (вся платформа + PostgreSQL + Kafka на 8–16 ГБ RAM).
- Хорошие библиотеки для Modbus (`goburrow/modbus`) и SNMP (`gosnmp/gosnmp`).
- Нативные Kafka-клиенты (`segmentio/kafka-go` / `twmb/franz-go`).
- Один бинарь на сервис — простое развёртывание в Docker без рантайма.
- Команда владеет Go.

## Последствия

**Позитивно:**

- Единый стек, единые подходы к логированию, конфигурации, HTTP-серверу.
- Низкие требования к железу на хосте.
- Хорошая производительность для ожидаемой нагрузки (2000–2500 тегов/с).

**Негативно:**

- Отсутствие богатых библиотек для бизнес-логики (например, сложная аналитика — пришлось бы тянуть внешние инструменты).
- Generics появились недавно — код местами многословный.
- Для тяжёлой аналитики/ML в будущем может потребоваться второй стек (Python).
