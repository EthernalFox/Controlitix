# 0043: viewer-ui — Дашборд объектов (главная страница оператора)

## Scope

`viewer-ui/src/`:
- `pages/DashboardPage/` — экран `/` (или `/dashboard`).
- `widgets/ObjectCard/`, `widgets/ObjectGrid/`.
- `features/objects-summary/` — store, селекторы, REST-клиент, WS-подписка.
- `shared/api/objects.ts` — REST-обёртки к `ms-viewer`.

Бэкенд `ms-viewer` — без изменений в этой спеке. Используем готовое:
- REST `GET /api/objects` (возвращает каталог объектов; см. 0029, § «Каталог»).
- WS group-subscription `object:<uuid>` (0034) — для live-агрегата по тегам объекта.
- REST `GET /api/alarms?status=active&object_id=<uuid>` (0033) — для подсчёта активных тревог.

Если в `ms-viewer` нет компактного эндпоинта «summary всех объектов сразу» — клиент собирает агрегат на месте (список объектов × counts из `/api/alarms`). Доводка backend — отдельной мини-спекой при профилировании.

## Context

Phase 6.2 роадмапа: «Дашборд объектов — список объектов с индикацией состояния (сколько активных тревог, статус устройств). Переход к мнемосхеме».

После логина (0027) оператор сейчас попадает на пустую `/` (placeholder из 0026). Спеки 0031 (Diagram), 0033 (Alarms), 0028 (Trends) дают экраны второго уровня, но не точку входа. Эта спека её закрывает.

Дизайн-референс — [docs/06_Дизайн/Design-Brief-viewer-ui.md](../docs/06_Дизайн/Design-Brief-viewer-ui.md), § «Дашборд». При его отсутствии — следовать паттернам Mantine `Card` + `Grid` и цветовой семантике из `Design-System.md` § «Цветовая семантика тревог».

## Interface

### REST contracts (используем готовое)

```ts
// shared/api/objects.ts
export interface ObjectSummary {
  id: string;
  name: string;
  description: string | null;
  diagramsCount: number;       // сколько опубликованных мнемосхем
  defaultDiagramId: string | null;  // первая опубликованная — для click-через
  devicesTotal: number;
  devicesOffline: number;      // backend заполняет на основе comm_loss-агрегата по объекту
}

export async function listObjects(): Promise<ObjectSummary[]>;
```

Если `ms-viewer` не отдаёт `devicesOffline` / `defaultDiagramId` — ставим заглушку (0/null) и заводим issue. В этой спеке не блокируемся на доделке backend.

### Подсчёт тревог

```ts
// features/objects-summary/model/objectsSummaryApi.ts
export interface ObjectAlarmCounts {
  alarm: number;     // lolo + hihi (unacked)
  warn: number;      // lo + hi (unacked)
  acked: number;     // active && acked
  bad: number;       // bad + uncertain
  comm: number;      // comm_loss + offline
}

export async function fetchActiveAlarmsByObject(): Promise<Map<string, ObjectAlarmCounts>>;
// внутри: GET /api/alarms?status=active&limit=500 → groupBy(object_id) → counts
```

Если сервер начинает отдавать > 500 активных — это сигнал к появлению эндпоинта-агрегата на backend (отдельной спекой).

### Store

```ts
// features/objects-summary/model/objectsSummaryStore.ts
type ViewState = "idle" | "loading" | "ready" | "error";

interface ObjectsSummaryState {
  status: ViewState;
  objects: ObjectSummary[];
  alarmCounts: Map<string, ObjectAlarmCounts>;
  lastError: string | null;

  load(): Promise<void>;            // вызывается на mount DashboardPage
  refresh(): Promise<void>;         // ручная кнопка
  applyAlarmEvent(e: AlarmEvent): void;  // из WS — инкремент/декремент counts
}
```

### Live-обновление

DashboardPage на mount:

1. `load()` — параллельно `listObjects()` + `fetchActiveAlarmsByObject()`.
2. Через `useTopicSubscription(["alarms"], handler)` (см. 0033) — подписка на глобальный alarms-топик.
3. На входящие `alarm`-frames с `event_type` ∈ `raised|cleared|acked` — `applyAlarmEvent` пересчитывает counts по `object_id` (резолв через `tag_id → object_id` уже есть в payload — см. 0033 DTO).

Подписки `object:<id>` per-card в этой спеке **не делаем**: глобальный `alarms`-топик уже содержит все нужные изменения; per-object усложнение дашборда не оправдано на 50–100 объектах.

### ObjectCard

Содержимое:

- Заголовок: `name` (truncate at 2 lines).
- Сабтайтл: `description` (если есть) или `«{devicesTotal} устройств»`.
- Бейдж тревог:
  - Если `alarm > 0` → красный «N тревог»;
  - Иначе если `warn > 0` → янтарный «N предупреждений»;
  - Иначе если `comm > 0` → серый «N offline»;
  - Иначе → нейтральный «OK».
- Полоса второстепенных счётчиков (если ненулевые): `acked: M`, `bad: K`.
- Иконка устройств: 🟢 если `offline == 0`, 🟡 если `offline < total/2`, 🔴 иначе. (Mantine icons из `shared/ui/components/Icon`, не прямой импорт.)

Карточка — `<Card>` из `shared/ui/components/Card` (фасад). `onClick` → `navigate('/diagrams/' + defaultDiagramId)` если он есть, иначе `navigate('/objects/' + id)` (страница-стаб со списком мнемосхем — out of scope; пока — placeholder либо disabled-карточка с тултипом «Нет опубликованных мнемосхем»).

### Empty/Loading/Error

- `loading` → 6 skeleton-карточек.
- `objects.length === 0` → центрированный Empty: иконка + «Нет объектов» + (для `admin`) кнопка «Перейти в editor-ui» (внешняя ссылка из env `VITE_EDITOR_UI_URL`).
- `error` → центрированный Error: текст + кнопка «Повторить» → `refresh()`.

## Constraints

- Никаких прямых импортов `@mantine/core` из `pages/DashboardPage` или `widgets/ObjectCard`. Только через `shared/ui/components` (фасад). Это правило проекта.
- Тексты — русский.
- Карточки кликабельны целиком (одна точка взаимодействия), не вложенные ссылки/кнопки внутри clickable-области.
- Не изобретать собственный механизм periodic-polling. Исходно — single-fetch + WS-обновления. Если WS отвалился (`RealtimeStatus = closed` из 0030) — показывать тонкий warning-баннер «Realtime недоступен. Данные могут устаревать» с кнопкой «Обновить».
- Подписка на топик `alarms` — единственная WS-команда со страницы. Не подписываемся на `object:<id>` пока нет ясного UI-требования.
- При unmount — обязательная отписка (через cleanup `useTopicSubscription`).
- Размер карточки фиксирован в Design-System (`var(--card-min-width)` ≈ 280px, height auto). Грид: `repeat(auto-fill, minmax(280px, 1fr))`.
- Не делать клиентскую сортировку по «severity»: backend отдаёт объекты в стабильном порядке (по `name`); сортировка по тревогам визуально путает оператора, который ищет известный объект по имени.
- Лимит `?limit=500` для `/api/alarms` — сознательная компромиссная константа. При приближении к лимиту в проде — поднимать `ms-viewer-alarms-aggregate-endpoint` спеку.

### 2. `alarms_batch` WS-сообщение не обрабатывается в DashboardPage

**Проблема:** `DashboardPage` подписывается только на одиночные `alarm`-события через `realtimeClient.on("alarm", ...)`. Начиная со спеки 0044, при групповом квитировании сервер отправляет `alarms_batch`-фрейм (с массивом событий), а не N отдельных `alarm`-фреймов.

Следствие: после группового квитирования (bulk ack из AlarmsPage) счётчики тревог на ObjectCard не обновляются до ручного `refresh()`. Пользователь видит устаревшие красные бейджи.

**Исправление:** добавить обработчик `alarms_batch` рядом с обработчиком `alarm`:

```tsx
// DashboardPage.tsx — useEffect
useEffect(() => {
  const unsubAlarm = realtimeClient.on("alarm", (message) => {
    applyAlarmEvent({ ...mapAlarmMessage(message) });
  });

  const unsubBatch = realtimeClient.on("alarms_batch", (message) => {
    for (const event of message.events) {
      applyAlarmEvent({ ...mapAlarmMessage(event) });
    }
  });

  return () => {
    unsubAlarm();
    unsubBatch();
  };
}, [applyAlarmEvent]);
```

Тип `"alarms_batch"` и форму payload взять из `viewer-ui/src/shared/modules/realtime` (должен присутствовать после реализации 0044 на фронтенде).
